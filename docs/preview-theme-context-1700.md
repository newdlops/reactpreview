# 프로젝트별 프리뷰 테마 상태 보존

0.1.1699의 CSS 레이어 수정으로 원본의 어두운 토큰이 실제 본문에도 적용되면서, 공용 웹뷰
저장소에 남은 `theme=dark`가 페이지 전체에 드러났다. 실제 VS Code의 새 진단 프리뷰에서
이 값을 읽었으며, 같은 시점의 시스템 다크 모드 선호는 false였다. 기존 검증의 새 브라우저
origin은 이 저장 상태를 재현하지 못했다. 원본 RootLayout은 기본 라이트 테마를 지정한다.

설치된 next-themes의 진짜 ThemeProvider를 작은 facade로 감싸 storageKey에 프로젝트 경로의
해시를 붙인다. 같은 프로젝트의 페이지는 키를 공유하고, 다른 프로젝트와 기존 공용 `theme`
키는 분리한다. 기존 값·설정·학습 기록은 삭제하거나 이관하지 않는다. 원본의 기본 테마,
forcedTheme, 시스템 선호, class/attribute, nonce와 사용자 전환은 그대로 Provider에 전달한다.
다른 localStorage 데이터나 앱의 인증 상태는 변경하지 않는다. 새 의존성은 추가하지 않는다.

추가로 테마 전환 UI 훅이 frozen frontier에서 대체값으로 바뀌던 원인을 확인했다. 실제
next-themes 상태와 setTheme, 적용된 class 읽기, 모션 선호와 시각 전환만 사용하는 동기 훅을
소스 구문으로 증명해 보존한다. 호출·자유 변수·import·모듈 초기화를 검사하며 fetch, 임의
전역/스토어, 알 수 없는 호출·효과·비동기 훅은 거부한다. 기존 64개 증명·1 MiB 한도와
모듈/소스 예산을 공유한다. 사용자 프로젝트나 package script는 실행하지 않는다.

검증은 `.tmp/preview-theme-context-1700-20261026t1844z/`에 보관한다. 이전의 실제 검색 페이지
고정 사본과 원본 의존성을 사용하며 원본 프로젝트는 읽기만 한다. 공용 키와 다른 프로젝트
키에 dark를 남긴 조건에서 기본 라이트 복원, 원래 버튼을 통한 양방향 전환, 프로젝트가
선택한 다크 모드와 390·768·1440px 화면을 검사한다. 외부 로그인·DB의 실제 응답은 범위에
포함하지 않는다. 기존 CSS 레이어 수정과 일반/무스타일 페이지의 가독성 회귀도 유지한다.

공용 dark가 남은 상태에서 검색·투자 페이지는 원본 라이트 토큰과 일치했고, 실제 버튼의
양방향 전환도 통과했다. 프로젝트 키에 명시한 dark도 유지했다. 두 최종 컴파일은 후속 빌드
0회, 번들링 약 5.04·5.05초였다. 반복 표본에 의한 성능 향상률로 해석하지 않는다.

737개 테스트 파일·5,783개 테스트를 포함한 `npm run check`와 production 빌드가 통과했다.
0.1.1700 darwin-arm64 VSIX를 설치했고 런타임 2,461개 파일이 패키지와 일치했다. 0.1.1699와
다른 런타임 파일은 컴파일 워커 하나다. 설치 직전·직후 설정/학습 파일 9개의 내용·권한을
비교해 보존을 확인했다. 이후 정상적인 프리뷰 검증에 의한 학습 업데이트는 허용했다.

실제 VS Code의 전용 검색 페이지 창에서도 같은 공용 웹뷰 origin을 사용한 라이트 화면,
원본 메뉴의 다크 전환, 라이트 복귀와 PAGE READY를 시각 확인했다. 콘솔에는 테마 훅의
대체값 메시지가 없었다. Next의 async Client Component/uncached promise 등 기존 render-only
호환성 메시지는 남으며, 이 변경으로 모두 해결했다고 주장하지 않는다. 사용자의 기존 창은
재로드하지 않았다. `Developer: Reload Window` 후 프리뷰를 다시 열면 새 워커를 사용한다.
