## 0.1.1691: 부모 import 비교의 반복 경로 계산 축소

한 소비 파일의 부모 JSX 분석에서 직전 import·소비 경로·대상 경로의 순수 비교와 대상 정규화만
재사용한다. alias 집합은 매번 확인하고 설정 기반 해석 결과는 저장하지 않는다. 전역 캐시·AST
보관·탐색 한도 변경은 없다. 48개 별칭의 비교용 경로 정규화는 96회에서 2회로 줄었다.
기존 구현과 문자열 비교 72,000건·부모 분석 480건의 결과가 같다. 새 워커의 실제 준비 6회에서
의존성·CSS·컨텍스트·진단은 같았고 모두 완료했다. Tax 두 쌍의 평균 번들링은 11.05→10.97초,
Node CPU는 25.04→24.30초였다. UDT 한 쌍은 번들링 1.95→1.73초이나 CPU는 1.5% 증가했다.
개별 시간은 양방향으로 변했고 표본이 적어 일반적인 속도·성공률 향상으로 해석하지 않는다.

## 0.1.1690: Page Inspector의 45초 분석 중단 제거

Page Inspector는 `fast`·`corridor`·`full` 모두 각 새 준비 단계에 기존 full 페이지와 같은
120초 한도를 적용한다. `fast`는 분석 범위를 선택하며, 정상적인 컨텍스트 탐색을 45초에
강제로 종료하지 않는다. 이 변경 자체가 분석·번들링 연산을 빠르게 만드는 것은 아니다.

같은 단계의 반복 보고는 한도를 연장하지 않고, 실제로 끝나지 않는 단계는 120초에 워커를
회수한다. 정지 판정까지의 대기 시간은 늘어날 수 있다. 사용자 취소·짧은 취소 응답 유예·
메모리 격리·대기 요청 재처리는 유지한다. 컴포넌트 단독 프리뷰와 명시한 호스트 제한은 그대로다.

## 0.1.1672: 교체한 화면의 styled-components CSS 수명

실제 VS Code IR 프리뷰에서 번들 교체 후 CSS 규칙이 469→918→1,347개로 누적됐다.
최초 현대식 런타임의 기본 삽입은 유지하고, 이후 교체만 공개 StyleSheetManager target을
사용한다. 이전 React 루트가 해제된 뒤 해당 교체의 스타일을 제거하며 초기 비소유 CSS는
삭제하지 않는다. 준비 중인 target은 분리 상태로 두어 실패·취소가 기존 화면을 바꾸지 않는다.

실제 React 18.3.1·styled-components 6.1.19 고정 데이터 검사에서 같은 공유 모듈을
한 번 평가하며 열 번 교체해도 표시 값이 같았다. 기존 규칙은 5→12개로 늘었고 변경 후에는
처음 5개, 이후 8개로 유지됐다. 원래 옵션 전달·비활성·legacy 경계와 최초 표시를 함께 검사한다.

네 실제 소스의 cold/warm·AB/BA 32회가 페이지·대상 출력과 CSS·의존성·진단·문맥을

새로고침을 확인했고 22개 화면을 직접 검토했다. 기존 생성 통계의 NaN, 대체 이미지·미디어와
Inspector wireframe 표시는 이번 CSS 수명 수정으로 해결됐다고 주장하지 않는다.

관찰 메모리 최대는 Node 약 2.123GB·native 약 0.561GB·합산 약 2.651GB였다.
1초 표본은 순간 peak·종료 CPU를 놓칠 수 있으며 Chromium CPU·메모리는 이 수치에 포함하지 않는다.
컴파일러·Sass·그래프·타입·소스·유휴 정책은 바꾸지 않았다.

같은 번들의 새로고침 네 표본 중앙값은 108.55→87.05ms였지만, 전체 준비 시간은

## 0.1.1661: 취소·캐시 CSS 소유권과 반복 탐색·할당 개선

취소된 준비가 선택 모듈을 실행한 뒤 CSS 링크를 제거하면 ESM은 캐시되지만 prefix는 다시
실행되지 않았다. 실제 Chromium에서 30px가 필요한 화면이 14px로 남는 실패를 먼저 확인하고,
리터럴 상대 import 성공 뒤 현재 CSS를 재확인해 복구했다. 반대로 취소한 editor를 열지 않아도
다음 갱신에서 10px가 30px로 바뀌는 실패도 재현했다. 실행 기록과 실제 활성 모듈을 구분하고
준비 기록은 성공한 교체에만 합친다. 기존 페이지의 동시 import와 CSS가 나중에 생기는 캐시
모듈도 보존한다. 취소 후 캐시 복구와 미열람 스타일 배제를 실제 브라우저 영구 검사에 담았다.

교체 준비 중 이전 페이지가 늦게 연 캐시 모듈의 CSS도 교체 순간 제거되는 실패를 확인했다.
교체 직전에 실제 로드가 끝난 링크를 인계하고, 현재 CSS와 다르거나 아직 준비되지 않았으면
React 렌더 전에 기존 문서 교체 경로를 요청한다. 오래된 스타일을 잘못 적용한 채 완료로
응답하지 않는다. 실패·취소는 기존 링크를 유지하고 CSS만 바뀐 편집도 계속 반영한다.

네이티브 import 표현식·옵션·await 범위를 유지하며 호출 위치에서는 import.meta를 사용해
함수 인자의 전역 이름 가림을 피한다. 생성 형식은 chunks/styles-v2/로 구분한다. 후처리는
추가 전체 JS 문자열 복사 없이 최종 UTF-8 버퍼에 기록하고, 긴 속성 이름의 충돌 확인도
반복 전수 검색을 피한다. Unicode·중첩 옵션·고유 이름·최종 생성 바이트 용량을 회귀 검사한다.

한 탐색 요청에서는 후보 자격·기능별 분류와 네이티브 정렬 그룹을 공유한다. 같은 문자열
비교 결과의 Unicode 표기는 같은 순위를 줘 안정 정렬의 기존 순서를 보존한다. 파일 내용이나
파일시스템 답을 새로 저장하지 않고, 타깃별 점수·제외와 기존 탐색 한도는 유지한다.
페이지 후보 한 번과 reverse pivot 여섯 번의 7쌍 비교에서 전체 결과·순서 hash가 같았다.
VCMeighth 3054개 경로는 28.24→22.20ms(-21.39%),
VCMforth 3062개는 29.06→22.54ms(-22.43%)이며 모두 7/7쌍 개선이다.
사전 20%·5/7쌍 기준을 통과했다. 후보 선별 연산의 수치이며 전체 루트 탐색 개선율은 아니다.

필요한 CSS와 JS를 함께 읽되 선행 읽기만으로 CSS를 적용하지 않는다. 제어된 루프백 fixture에서
두 응답에 각각 200ms 지연을 주고 새 문서로 7쌍 AB/BA를 비교했다. 첫 선택 모듈 스타일 준비는
404.3→202.2ms(-49.99%), 7/7쌍 개선이었다. CSS 요청은 각 1회이며 글꼴·평가 횟수와
열지 않은 화면의 지연 로딩을 유지했다. 사전 25%·5/7쌍 기준을 통과한 전송 지연 검사 수치다.

실제 VCM InvestorInfoSection은 같은 esbuild 모듈·네이티브 위치와 최종 production 바이트로

## 0.1.1660: 캐시된 모듈의 CSS 복구와 반복 탐색 감소

같은 문서 새로고침에서 브라우저가 캐시한 ESM 모듈의 prefix를 다시 실행하지 않아 필요한
CSS 링크를 제거하던 문제를 수정했다. 앞선 0.1.1659 기록에서 원본 제약으로 분류했던
새로고침 뒤 가로 넘침은 이 CSS 유실과 연결돼 있었다. 새 revision은 실제 실행된 모듈의
CSS를 복구하고 CSS만 바뀐 편집도 반영한다. 한 번도 열지 않은 모듈의 CSS는 불러오지 않는다.
교체 CSS는 기존 순서의 비활성 링크로 준비하고 React 배치 효과 전에 적용한다. 준비 실패·

## 0.1.1657: 새로고침의 스타일·페이지 유지와 조회 비용

설치된 styled-components의 타입 선언과 실제 JavaScript 진입점 이름이 다르면 기존 공유 런타임

## 0.1.1651 추가: Inspector의 불필요한 라우터 보정 빌드

목록 페이지의 첫 native build에서 넓은 frontier는 provider 소유권을 추정했지만, 실제
실행 그래프에는 그 provider가 없었다. 전역 자동 래핑 플래그 하나만 달라 전체 빌드를
다시 수행했다. Page Inspector는 그 플래그를 사용하기 전에 반환하며 후보별 소유권·상속
문맥으로 Router를 처리한다. 따라서 Inspector에서 활성 라우터의 전역 플래그를 일관되게
선택하고, 일반 컴포넌트의 소유권 처리와 라우터 활성화 변경의 보정 빌드는 유지한다.
실제 도달 그래프의 소유권 근거는 수정하지 않고 기존 캐시에 그대로 기록한다.

설치됐던 0.1.1651 워커와 수정 워커를 새 워커 5쌍 AB/BA로 비교했다. 목록 첫 요청의
native build는 모든 쌍에서 2→1회였다. 아래는 최초 전체 비교의 집단별 중앙값이다.
다른 CPU 작업 때문에 시스템 부하가 높았으며, 실패한 보존 판정도 그대로 남긴다.

최초 실패 판정을 숨기지 않는다. 앱이나 모든 재준비가 빨라졌다는 결론은 내리지 않는다.

별도 계획을 먼저 기록하고 작은 예제를 새 부모 프로세스에서 추가 검증했다. 같은 원래

작은 예제의 느려짐은 이 추가 실행에서 재현되지 않았다. 이를 작은 예제의 확정된 개선율로
해석하지 않으며, 최초 5쌍과 추가 대조 표본을 모두 보관한다.

실제 목록은 새 워커·새 Chromium 프로필 3쌍으로 전체 실행도 별도 비교했다. 컴파일 요청부터
Chromium의 ready·안정화와 브라우저 자원 정리까지 중앙값은 59,949→43,463ms(27.5% 감소),
더 빠른 쌍은 3/3이었다. 6회 모두 같은 그래프와 대상 DOM을 유지했다. 컴파일러 종료 시간은
제외하며, 실제 VS Code 첫 화면이나 반응형 시각 검증 시간은 아니다. 공유 부하·OS 캐시의
영향을 받는 소표본이고 앞의 컴파일 전용 측정과 시간을 합치지 않는다.

작은 예제·앱·목록의 별도 Chromium 산출물 검사도 6/6 ready였고 대상 DOM이 바이트 단위로
같았다. window·CDP·필수 산출물 오류는 없었다. 대형 대상의 기존 console 기록 13건은
수정 전후 동일하게 남는다. 브라우저·서버·프로필·워커를 종료했고 산출물 서버는 전용
루프백 `127.1.0.1`에서만 열었다. 사용자 프로젝트의 서버·설정·스크립트는 실행하지 않았다.

브라우저 산출물 45개 중 42개는 원시 바이트가 같다. 나머지 진입 코드 3개는 정확한

바이트 단위로 같고, 진입 코드는 두 정확한 생성 식별값 선언만 제외하면 같다. 실제 식별값
생성·검증은 그대로다. Chromium에서 대상 출력·중첩 마운트·활성 blocker 0, 안정화된 ready와
브라우저·프로필·127.1.0.1 서버 정리를 확인했다. 기존 partial 문맥·데이터 대역을 유지한다.
VS Code 창의 재로드·반응형 화면·실제 API 제출은 이번 변경에서 다시 검증하지 않았다.

## 0.1.1646: 번들 분석의 중복 파싱 제거

번들 소스의 문법 오류 검사와 런타임 import 수집이 하나의 구문 트리를 사용한다. 두 분석의
확장자별 파서 옵션·진단·타입 전용 제외·방문 순서·정확한 위치·동결 결과는 유지한다.
반환 결과에는 AST를 넣지 않으며 별도의 AST 캐시나 파일시스템 캐시도 추가하지 않는다.

훅 투영은 기존의 호출 증거를 먼저 검사한다. 허용된 호출이 없는 파일은 원래도 빈 투영을
반환하므로 후속 렌더 그래프 분석을 생략한다. 실제 훅이 있는 파일의 혼합 import·별칭·fallback
조건과 깊이·개수 제한은 같다. 오류 문법·TS/TSX 구분·실제 edge·위치·훅 편집/제거를 검사한다.

실제 FiStaApp을 0.1.1645와 변경 후 production 워커에서 읽기 전용으로 비교했다. 동일한
의존성 조회 위치와 4GiB 힙을 사용했다. 첫 회차는 AB/BA/AB/BA/AB의 버전별 새 워커 5개,
추가 회차는 AB/BA/AB의 버전별 새 워커 3개다. 두 회차를 모두 보관하며 각 워커에서 첫 준비와
동일 요청의 재준비를 측정했다. 다른 테스트·프로파일러와 분리했고 원본 서버는 실행하지 않았다.

| 준비 시간 중앙값       | 0.1.1645 | 0.1.1646 |   감소 |
| ---------------------- | -------: | -------: | -----: |
| 첫 회차 5회: 첫 번들   | 31,855ms | 35,617ms | -11.8% |
| 첫 회차 5회: 재준비    | 19,250ms | 22,994ms | -19.4% |
| 추가 회차 3회: 첫 번들 | 19,125ms | 16,445ms |  14.0% |
| 추가 회차 3회: 재준비  | 12,892ms | 11,511ms |  10.7% |

첫 회차의 첫 준비 Node CPU 중앙값은 31,319→30,262ms
(3.4% 감소), 재준비는 16,590→16,281ms (1.9% 감소)였다.
추가 회차의 첫 준비 Node CPU 중앙값은 24,478→21,404ms
(12.6% 감소), 재준비는 12,640→12,117ms (4.1% 감소)였다.
CPU 값은 호스트와 워커의 사용자·시스템 시간을 합치며 별도 native esbuild 프로세스는 제외한다.

첫 회차 중 CPU idle 0.43%·압축 메모리 18GB, 추가 회차 시작 전 idle 41.59%를 관찰했다.
부하 변화가 큰 환경이며, 첫 회차에서는 실제 대기 시간이 오히려 증가했다. 추가 회차의 감소율을
모든 실행의 개선으로 해석하지 않는다. 개발서버와 직접 비교하지 않았으며 첫 번들 준비 시간은
화면의 첫 DOM commit이나 전체 안정화 시간과 구분한다.

두 회차의 모든 활동 기록·번들 요약·의존 경로·문맥 범위가 같다. 청크 22개와 CSS는 기존
0.1.1645 출력과 바이트 단위로 같고, 진입 코드는 매번 생성되는 두 정확한 식별값 선언만 제외하면
같다. 실제 식별값 생성·검증은 그대로다. Chromium에서 대상 출력·중첩 마운트·활성 blocker 0과
안정화된 ready, 브라우저·프로필·전용 루프백 서버 종료를 확인했다. VS Code 창·반응형 화면은
이번 변경에서 다시 검사하지 않았다. 기존 부분 문맥과 데이터 대역을 유지하며 실제 API 제출은 검사하지 않았다.

같은 작업에서 실험한 타입 해석 메타데이터 캐시는 조회 횟수만 줄고 전체 준비 시간과 CPU가
증가해 철회했다. 해당 캐시·테스트 의존성·시스템 변경은 이번 배포에 추가하지 않는다.

## 0.1.1645: 반복 훅 사용 탐색과 경계 증거 재사용

같은 함수의 훅 바인딩마다 전체 본문을 다시 방문하던 세 분석을 식별자 색인으로 제한한다.
추적 이름이 포함된 하위 구문의 상위 노드도 남기며 원래 순서·shadowing·사용 경로·방문 한도를
유지한다. 색인은 해당 AST가 회수될 때 함께 회수되며 새 편집 AST와 공유하지 않는다.

문맥에 의존하지 않는 훅 경계 증거는 정확한 경로와 소스가 같을 때 재사용한다. 최대 512개,
문자열과 숫자 위치의 환산 보관량 4MiB, 개별 소스 64Ki 코드 단위로 제한한다. AST·파일시스템
상태·브라우저 판정은 저장하지 않는다. 빈 결과와 큰 소스는 보관하지 않고, 편집 시 이전 증거를
버린다. 타입 프로그램·Provider·Router·실행 그래프·브라우저 성공 판정은 기존대로다.

실제 FiStaApp을 0.1.1644와 변경 후 production 워커에서 읽기 전용으로 비교했다.
동일한 의존성 조회 위치·4GiB 힙으로 AB/BA/AB를 두 차례 실행해 버전별 새 워커 6개를 측정했다.
두 번째 회차에는 Node의 process.cpuUsage로 CPU 사용자·시스템 시간을 함께 읽었다. 별도
프로파일러·테스트·사용자 프로젝트 서버·OS 캐시 조작을 함께 실행하지 않았다.

| 준비 시간 중앙값, 버전별 6회 | 0.1.1644 | 0.1.1645 |  감소 |
| ---------------------------- | -------: | -------: | ----: |
| 첫 번들 수신                 | 20,752ms | 19,097ms |  8.0% |
| 같은 워커 재준비             | 13,506ms | 10,900ms | 19.3% |

CPU 계측 회차의 첫 준비 Node CPU 중앙값은 26,742→24,316ms
(9.1% 감소), 재준비는 14,612→12,258ms
(16.1% 감소)였다. 이 CPU 값은 호스트와 워커를 합치며 별도 esbuild
프로세스는 포함하지 않는다. 개별 준비 시간의 편차는 여전히 크며 개발서버와 직접 비교한
수치는 아니다. 첫 번들 수신 시간과 VS Code 화면의 첫 DOM commit·전체 안정화 시간도 구분한다.

모든 비교의 활동 기록·의존 경로 2,253개·번들 크기·청크 22개가 같았다. 저장한 브라우저 출력도
청크 22개와 CSS가 바이트 단위로 같고, 진입 코드는 정확한 두 생성 식별값 선언만 제외하면 같다.
실제 제품의 식별값 생성·검증은 바꾸지 않았다. 세부 검사와 시각 검증은 각 실행 기록에 남긴다.
