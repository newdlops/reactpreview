# 0.1.1692: 반복 훅 필드 분석의 문법 순회 축소

같은 함수의 여러 훅 필드를 분석할 때 `const` 선언과 중첩 함수의 변수 이름을 반복 수집했다.
정확한 `collection[0]` 별칭과 기존 이름 충돌 판정만 불변 구문 트리에서 한 번 준비한다.
별칭 목록은 함수 노드를 키로 하는 약한 참조에 보관하며 구문 트리와 함께 회수된다.
임시 선언·이름 집계는 인덱스 구축 후 버린다. 소스·파일 경로를 강하게 보관하는 캐시는 없다.

별칭을 사용하는 자식의 요구 정보, 외부 helper·타입 판단, 선택한 대상, 호출 깊이와 대체 값은
저장하지 않는다. 같은 구문 트리의 자식 요구 정보가 바뀌면 새 값을 다시 계산한다.
다시 파싱한 편집은 이전 트리의 목록을 사용하지 않는다. 중첩 이름 충돌, 중복 선언, `let`,
`?.[0]`, 계산된 인덱스와 0 이외의 인덱스를 제외하는 기존 규칙을 유지한다.
탐색 범위·횟수·분석 깊이·메모리 한도와 Page Inspector 단계당 120초 정책도 유지한다.

49개 바인딩을 질의하는 검사에서 문법 방문은 12,397회에서 253회로 줄었다. 같은 부모·위치·
구문 속성을 유지하며 합성 변환 540건과 실제 소스 160개의 출력이 기존 구현과 같다.
관련 static-resource 검사 638개가 통과했다. 이 수치는 실제 페이지의 총 준비 시간과 구분한다.

실제 production SDK를 별도 새 워커에서 읽기 전용으로 비교했다. Tax 세 쌍과 UDT 한 쌍의
총 8회를 모두 보존했으며 프로파일링 표본은 시간 비교에 넣지 않았다. 초기 결과가 엇갈려
Tax 한 쌍을 추가한다고 먼저 정한 뒤 실행했다. OS 캐시나 사용자 프로젝트는 변경하지 않았다.

| 표본 평균         | 0.1.1691 | 0.1.1692 |
| ----------------- | -------: | -------: |
| Tax 전체 준비     |  17.52초 |  17.51초 |
| Tax 컨텍스트 탐색 |   2.17초 |   2.30초 |
| Tax 번들링        |  12.04초 |  12.06초 |
| Tax Node CPU      |  25.79초 |  25.85초 |
| UDT 전체 준비     |   2.98초 |   2.42초 |
| UDT 번들링        |   2.18초 |   1.74초 |
| UDT Node CPU      |   4.36초 |   3.99초 |

모든 비교의 의존 경로·CSS·컨텍스트·진단이 같고 8회 모두 완료했다. 개별 시간은 양방향으로
변했다. Tax 탐색은 평균 5.9% 길었고 전체 준비와 CPU는 거의 같았다. UDT는 한 쌍뿐이므로
전체 프로젝트에 대한 속도·렌더링 성공률 향상으로 일반화하지 않는다. 이번 변경의 확실한
효과는 반복되는 문법 순회를 줄이면서 매번 필요한 문맥 판단을 유지하는 것이다.
