# 렌더링 분기와 탭 상태 복구 — 0.1.1679

RTCC의 `HeavyTaxEditModal`은 상세 페이지 URL을 올바르게 선택한 뒤에도 단계 구성 helper가
불변식 오류를 던져 모달에 도달하지 못했다. JSX 소유 관계에는 포함되지 않은 반환 함수 호출이
실제 렌더링 경로에 있었고, 그 아래 URL 기반 탭 훅도 생성 값으로 대체되어 있었다.

## 변경과 제한

- 실제 실행 후보의 인접 렌더링 단계를 이용해 비 JSX 함수 호출의 원본 위치도 연결한다.
  관계없는 파일 전체를 추가 탐색하지 않는다.
- 동기 export helper가 매개변수 별칭, 단순 분기, imported 함수 반환과 마지막 오류로만
  구성되고 선택한 반환이 유일한 경우에 한해 조건을 계측한다. 자동 선택은 실제 값이 Boolean이고
  현재 후보의 소스·소유 함수·직전 호출 대상이 모두 일치할 때만 적용한다.
- 사용자 조건 선택, 복구 결과, 자동 값 비활성화와 REST 행 제공 중의 기존 처리도 유지한다.
  객체·배열·누락 데이터를 Boolean으로 바꿔 통과시키지 않는다.
- React의 상태 훅과 Router의 location/navigation을 사용하는 쿼리 UI 훅은 별도로 증명한다.
  effect에는 쿼리 읽기와 로컬 상태 변경만 허용한다. 이벤트의 navigation은 현재 pathname의
  쿼리 변경으로 한정한다. 임의 import·호출·전역 변경·데이터 요청·비동기 함수는 인정하지 않는다.
- `Tab`의 유일한 spread, 배열 구조분해로 받은 controller, 원본 `TabItem`의 고정 event key와
  선택한 자식 컴포넌트가 연결될 때만 훅의 초기 기본값을 감싼다. 해당 imported 훅의 구현도
  위 소스 검사를 통과해야 한다. 기존 런타임 훅 계측으로 감싼 호출도 동일하게 처리한다.
- 실제 훅이 URL 값을 기본값보다 먼저 사용하며, 이후 `activeKey`·`onSelect`는 원본 상태와
  이벤트 처리에 맡긴다. 동적 키, 중복 키, 여러 탭에 걸친 대상, controller 재사용·shadowing은
  초기 선택을 추가하지 않는다.

기존 프런티어의 64회·파일당 32KiB·총 1MiB 검사 한도는 유지한다. 초기 탭 기본값에 필요한
별도 증거는 빌드당 최대 32회·파일당 32KiB·총 512KiB이며 결과만 요청 안에 보관한다.
추가 의존성·상주 서비스·예약 등록은 없다. 워커와 네이티브 번들러의 기존 자원 상한도 유지한다.

## 검증

선택한 imported 반환, 모호한 호출, 부수효과·변경·비동기 코드, 실제 Boolean 값, 현재 후보의
소스·함수·호출 불일치, 수동 선택과 자동 값 해제를 검사했다. 쿼리 UI 훅의 effect·이벤트 경계,
shadowing, 초기 탭 기본값과 기존 훅 계측의 조합, import 증거와 검사 예산도 회귀 검사한다.

전체 `npm run check`에서 5,471개 통과·10개 실패를 확인했다. 실패 항목은 0.1.1678과 동일하며
`127.1.0.1` 바인딩 오류가 남아 있다. 전체 통과로 표현하지 않는다. 줄 수·타입·lint·format은
통과했다. 실제 화면 검증은 TCP listener 없이 CDP pipe와 Fetch interception으로 실행한다.
주소·관리자 권한·자동 실행·보안·VPN 정책을 변경하지 않는다.

## 같은 입력 6개 비교

설치된 0.1.1678과 최종 후보 SDK를 같은 읽기 전용 입력에서 순차 실행했다. 사례별 실행 순서를
번갈아 배치했고 다른 컴파일·전체 검사와 겹치지 않았다. 아래 시간은 초 단위다. 컨텍스트와
번들링은 첫 준비, 누적 준비는 제품이 실제 요청한 복구 컴파일도 포함한다.

| 입력                 | 최초 컨텍스트 |   최초 번들링 |     누적 준비 | 최종 상태                       |
| -------------------- | ------------: | ------------: | ------------: | ------------------------------- |
| RootLayout → Profile |   0.30 → 0.35 | 15.66 → 12.37 | 18.85 → 15.15 | 정상 유지                       |
| Loans                |   0.13 → 0.06 | 11.36 → 13.82 | 15.09 → 16.83 | 정상 유지                       |
| Investment           |   3.54 → 1.98 |   6.55 → 7.50 | 11.64 → 10.97 | 정상 유지                       |
| MeetingDeleteModal   |   3.86 → 1.69 |   6.41 → 7.74 | 15.90 → 12.34 | 정상 유지                       |
| HeavyTaxEditModal    |  8.82 → 13.51 | 21.06 → 28.47 | 94.74 → 51.39 | 실제 페이지 안의 모달 정상 출력 |
| TaxAndFeeTables      |   4.43 → 4.65 | 19.68 → 16.94 | 51.51 → 49.57 | 상위 페이지 데이터 오류 남음    |

정상 렌더링은 4/6 → 5/6이다. HeavyTax의 host 재컴파일은 1회 → 0회로 줄었다.
최초 준비 합계는 126.41 → 132.95초로 약 5% 늘었지만, 복구를 포함한 누적 준비는
207.73 → 156.24초로 약 25% 줄었다. 누적 컨텍스트는 42.21 → 26.35초, 누적 번들링은
128.22 → 102.81초였다. 모든 파일의 최초 준비가 빨라졌다고 주장하지 않는다.
사례당 한 쌍의 관측치이므로 p95나 일관된 개선을 입증하지 않는다.

Node CPU는 229.44 → 192.17초, 네이티브 CPU는 45.16 → 37.53초였다.
관측한 합산 RSS 피크는 2,999.00 → 2,950.30MiB로 약 2% 낮아졌다. 사례별 피크 변화는
약 -22.08%~+4.96%였다. 기존 자원 상한을 높이지 않았고 대상 번들 의존성은 HeavyTax와
Tax에서 각각 훅 모듈 한 개가 추가되었다. SDK 크기 증가는 약 21KiB다.

6개 사례의 첫 CSS 바이트는 이전 버전과 동일하다. 390×844, 768×1024, 1440×900에서 화면을
확인한다. 기존 정상 네 사례는 메뉴·Escape, 라디오 이동, 검색·숫자·확인 문구와 Tab 입력을
실제 마우스·키보드로 검사했고 문서 가로 넘침이 없다. HeavyTax는 전환이 끝난 모달의 배경과
조상 opacity가 모두 1인 상태를 별도로 확인했다. 동일한 미수정 번들에서 Inspector의 공개 props
선택으로 모달만 잠시 숨기고, 실제 탭 클릭·ArrowLeft 이동·복원을 검사한 뒤 선택을 해제했다.
저장·삭제·수정 제출은 하지 않았다.

HeavyTax의 배경 원본 페이지는 작은 화면에서 폭 901px을 유지한다. 모달은 뷰포트 안에 맞지만
배경의 가로 스크롤까지 해결한 것으로 표현하지 않는다. 실패한 Tax 페이지의 가로 스크롤과
500 오류도 결과에 남긴다. 원본 CSS를 숨기거나 덮어써 검사 결과를 맞추지 않는다.

## 남은 데이터 문제

`TaxAndFeeTables`의 현재 수정 페이지 경로에서는 생성된 안건 문자열이 원본 안건 그룹의
허용 값에 포함되지 않아 `Group for Agenda selection not found` 오류가 발생한다. 분리된 표의
출력이 있어도 상위 페이지의 500 오류를 정상 렌더링 성공으로 계산하지 않는다.
이 오류를 숨기거나 원본 허용 목록을 변경하지 않았다.
