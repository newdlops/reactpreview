# 이전 프리뷰 로딩 최적화 기록

원래 검증 내용과 한계를 보존한 기록이다.

## 0.1.1644: 필요한 JSX 전달에서 자식 계약 분석

props 또는 훅 결과가 자식 JSX의 속성으로 정확히 전달될 때 자식 계약을 수집한다. 훅을 쓰지
않거나 반환값을 무시하는 모듈, 별개 값만 자식에게 넘기는 모듈은 해당 탐색을 실행하지 않는다.
직접 전달·별칭·구조 분해·배열 항목·spread의 기존 경로 증거와 shadowing 검사를 유지한다.
같은 소스의 여러 전달은 계약을 한 번만 수집하며, 새 소스 변환과 공유하지 않는다.

매개변수가 없는 일반 함수는 원래도 props 추론 결과가 없으므로 먼저 반환한다. 클래스의
`this.props` 분석은 유지한다. 타입·전이 깊이·실행 그래프·Provider/Router 소유권·실제 경로
제한·브라우저 성공 판정·워커 메모리 한도는 바꾸지 않았다. 파일시스템 및 상위 함수 탐색 캐시
실험은 이득을 분리해 확인하지 못해 최종 변경에서 제외했다.

2026-10-17, macOS arm64 / Node 22.22.2에서 실제 FiStaApp 소스를 읽기 전용으로 비교했다.
0.1.1643과 변경 후 production 워커를 같은 깊이의 임시 경로에 두고 동일한 의존성 경로를
전달했다. 버전별 새 워커 3개를 AB/BA/AB 순서로 교대 실행했고, 각 워커에서 첫 준비와 같은
요청의 재준비를 측정했다. 원래의 4GiB 힙 한도를 유지하고, 테스트·프로파일러·파일 조회 계측과
분리했다. OS 캐시나 시스템 정책을 바꾸거나 사용자 프로젝트 서버를 시작하지 않았다.

| 실제 페이지 준비 중앙값 | 0.1.1643 | 0.1.1644 |  감소 |
| ----------------------- | -------: | -------: | ----: |
| 첫 번들 수신            | 22,451ms | 19,171ms | 14.6% |
| 같은 워커 재준비        | 19,573ms | 12,857ms | 34.3% |

초기 준비의 개별 값은 기준 33,976/22,451/15,820ms, 변경 후 17,830/19,171/30,851ms였다.
시간 편차가 크고 마지막 쌍은 변경 후가 더 느렸다. 초기 준비 20% 감소라는 작업 중 목표는
달성하지 못했다. 이 소표본의 중앙값 감소를 모든 실행의 개선, 서버보다 빠른 로딩, VS Code의
전체 화면 안정화 또는 첫 DOM commit 시간의 개선으로 해석하지 않는다.

6회 모두 번들 7,993,251바이트·청크 22개·의존 경로 2,253개와 경로 목록 해시가 같았다.
각 단계의 활동 기록도 같았으며, authored 모듈 274개·exact 7개·support 214개·optional 53개,
깊이 8과 native build 1회를 유지했다. 오류 진단은 없었고 문맥 범위는 기존처럼 `partial`이다.
이 일치만으로 실제 페이지 렌더 성공을 판정하지 않는다.

별도 출력 비교에서는 브라우저 청크 22개와 CSS가 바이트 단위로 같았다. 진입 코드도 매번
생성되는 런타임 식별값과 소스 제스처 비밀값의 두 정확한 선언만 제외하면 같았다. 실제 제품의
식별값 생성·검증 코드는 수정하지 않았다. 전체 `npm run check`는 635개 파일·4,954개 검사를
통과했고, 측정한 production 워커와 설치한 0.1.1644의 워커 해시 및 런타임 파일 2,460개를 확인했다.

실제 Chromium은 목록 경로에서 안정화된 `ready`, 대상 출력, 중첩 마운트, 활성 blocker 0개를
확인했다. 새 VS Code 창에서는 Inspector의 경로 선택으로 목록→만들기→중첩 앱→사용자 정보→목록을
확인했고, 중첩 두 화면에서 원래 `FiStaManagementAppContextProvider` 마운트를 확인했다.
사용자 정보 화면의 실제 CSS 크기 390×844·768×1024·1440×900에서 화면을 보고 가로 넘침이
없음을 읽기 전용 DOM 측정으로 확인했다. 모바일 스크롤 입력 뒤의 이동 수치는 확정하지 않았다.

목록 안의 만들기 버튼만 누르면 빈 본문이 되는 경우가 관찰됐고, Inspector에서 해당 경로를
선택하면 다시 준비해 정상 출력했다. 이 직접 이동을 성공했다고 집계하지 않았다. native 콘솔에는
MUI 진단과 403·CSP로 차단된 소스맵 요청도 있어 콘솔 오류가 전혀 없다고 주장하지 않는다.
기존 자동값을 사용했으며 실제 백엔드 데이터나 폼 제출은 검증하지 않았다. 검증 후 표시 도구와
DevTools를 복원하고 검증 창을 닫았다.

아래 0.1.1519 이하의 측정과 검사 제한은 해당 과거 버전에 대한 기록이다.

## 0.1.1519: 중복 검사와 준비 실패 재시도

전체 호환성 변환이 필요한 모듈은 비싼 pass-through 사전 검사 전에 제외한다. 나머지 모듈의
사전 검사 결과는 정확한 경로·소스 문자열이 같을 때만 재사용한다. 최대 128개이며 경로와 소스의
UTF-16 환산 문자열 저장량은 1MiB, 개별 소스는 64Ki 문자로 제한한다. AST·변환 결과·파일시스템
상태는 캐시하지 않는다. 편집된 소스·다른 파서 문법·파서 오류는 기존 fail-closed 검사를 유지한다.

자체 TSX 모듈 80개를 3회 판정하는 교대 순서 측정 6쌍에서 파서 호출은 480→80회였다.
모든 판정 결과의 SHA-256이 같았다. 이는 **사전 검사 작업량**의 감소이며, 전체 컴파일이나 화면
완료 시간을 83% 줄였다는 뜻이 아니다. 데이터·훅 추론의 분석 깊이와 최종 실행 그래프 검증은 그대로다.

실제 대형 페이지를 같은 설정으로 배포용 워커에서 읽기 전용 비교한 첫 소표본은 다음과 같다.

| 측정               | 0.1.1518 |  변경 후 |
| ------------------ | -------: | -------: |
| 초기 준비 1회      | 20,194ms | 27,349ms |
| 같은 워커 재준비 1 | 10,065ms | 11,892ms |
| 같은 워커 재준비 2 | 11,426ms | 10,793ms |

이 측정에서는 **전체 준비 시간 개선을 확인하지 못했다**. 변경하지 않은 탐색 단계부터 시간 변동이
있었으며 시스템의 다른 프로세스 부하도 관찰됐지만, 이를 지연의 확정 원인으로 단정하지 않는다.
두 버전 모두 의존 경로 2,932개·청크 19개·오류 진단 없음·partial 문맥이었다. 변경 후 비교 번들은
새 복구 제어 코드 때문에 2,591바이트 커졌다. 사용자 프로젝트를 실행하거나 렌더 성공으로 집계하지
않았으며, 이후 메시지 상관관계·리비전 검증과 실패 예산을 강화한 최종 번들의 성능 수치는 아니다.

자동 페이지 선택의 `build-failed`와 `selection-unavailable`은 현재 표시 리비전에서만 후보를
제외한다. 호스트 요청이 해제된 다음 미시도 후보를 평가하고, 준비 실패 3회 또는 후보 소진 후에는
자동 빌드를 멈춘다. 마지막 정상 프리뷰·수동 재시도는 유지하며 새 리비전에서 다시 후보를 허용한다.
취소·busy·발행 실패·시간 초과는 후보 실패로 학습하거나 자동 반복하지 않는다. 수동 선택·일시정지·
대상/소스 변경·오래된 응답은 재시도 소유권을 얻지 못한다. 가중치·학습 기록·실제 연속 출력 검증은
바꾸지 않았다. 이 재시도 회귀의 통과를 실제 프로젝트 전체 성공률 상승으로 해석하지 않는다.

변경부 회귀 243건과 실제 Chromium의 두 모드 시작·setup 실패·수정 후 복구 6개 시나리오를 통과했다.
추가 컴파일러 회귀는 42건 중 39건 통과했다. Context 필드·fragment carrier·선택적 form 상태 추론
3건은 이번 컴파일러 변경 두 파일만 메모리에서 이전 내용으로 바꾼 대조 실행에서도 동일하게 실패했다.
새 테스트 32건은 모두 통과했고 strict typecheck·production build·변경 범위 ESLint·Prettier도
통과했다. `npm run check`는 기존 51개 파일의 1,000줄 제한 위반으로 중단됐다. 실제 사용자 VS Code
창의 시각 검증이나 전체 현장 성공률 측정은 수행하지 않았다.

## 0.1.1518: 실제 페이지 재준비의 중복 빌드

실제 대형 워크스페이스의 동일 페이지를 배포용 워커로 읽기 전용 컴파일했다.
프로파일에서 초기 frontier의 라우터 소유권 추정이 실제 도달한 그래프와 달랐으며,
이전 빌드의 정확한 부정 근거를 초기 추정과 OR 결합해 재준비마다 같은 보정 빌드를 반복했다.
현재 편집 대상의 직접 근거는 유지하면서, 이전 도달 그래프를 넓은 frontier 추정보다 우선한다.
최종 그래프 비교는 그대로 수행하므로 의존 소스에 provider를 추가·제거하면 보정 후 발행한다.

로컬 helper 선언 색인은 같은 파서 트리 안에서만 `WeakMap`으로 재사용한다. 트리가 회수되면
색인도 회수되며, 같은 파일명의 새 편집 AST와 공유하지 않는다. import 경로 결과는 resolver
인스턴스 안에서 성공 결과만 최대 4,096개 보관하고 importer·specifier가 다른 요청을 구분한다.
일반 package edge는 Yarn PnP의 React DOM companion 후보가 아니므로 파일시스템 조회 전에 제외한다.
분석 깊이·그래프 범위·복구 후보·사전학습 가중치·브라우저의 성공 조건은 줄이지 않았다.

2026-09-08, 같은 소스와 설정으로 버전별 새 워커에서 fast 요청을 3번 연속 실행했다.
각 첫 요청은 초기 준비이며, 뒤의 2번이 같은 워커의 재준비다. 테스트·프로파일러와 분리했다.

| 실제 페이지 측정      |   0.1.1517 |  0.1.1518 |
| --------------------- | ---------: | --------: |
| 초기 준비 1회         |   15,698ms |  18,775ms |
| 재준비 1              |   13,815ms |   8,543ms |
| 재준비 2              |   17,562ms |   9,246ms |
| 재준비 평균           | 15,688.5ms | 8,894.5ms |
| 재준비당 native build |        2회 |       1회 |

이 소표본에서 재준비 평균은 43.3% 감소했지만 **초기 준비 개선은 확인하지 못했다**.
초기 준비는 계속 보정 빌드 2회가 필요하며, 시스템 부하에 따른 시간 변동도 크다.
15초 유휴로 워커가 회수되면 재준비 캐시 역시 유지되지 않는다. 순차 측정이며 실제 VS Code의
전체 화면 로딩·복구 완료 시간이나 다른 프로젝트의 속도 향상을 보장하지 않는다.
두 버전의 출력은 JavaScript 14,631,480바이트, 청크 19개, 의존 경로 2,929개로 같았고,
오류 진단 없이 partial 문맥을 반환했다. 이를 페이지 전체 렌더 성공으로 해석하지 않는다.
관찰 로그의 별도 `rrweb` 누락 실패는 이 기본 후보 재현에서는 발생하지 않았으며,
사용자 의존성을 자동 설치하거나 실패 import를 임의로 제거하지 않았다.

검증: 관련 446건 중 431건 통과. 나머지 15건은 이번에 변경한 소스 5개만 이전 내용으로
교체한 메모리 내 대조 실행에서도 동일하게 실패했다. 새 회귀는 없었으며, 실제 Chromium의
두 모드에서 시작·공유 모듈 로딩·setup 실패·수정 후 재시작 6개 시나리오도 통과했다.
strict typecheck·production build·변경 범위 ESLint·Prettier는 통과했고, `npm run check`는
기존 51개 파일의 줄 수 제한 위반으로 중단됐다. 실제 사용자 VS Code 화면은 시각 검증하지 않았다.

## 0.1.1517의 변경 범위

확장 자체의 Node 번들에서만 TypeScript 기본 import를 하나의 facade로 모았다.
각 분석 모듈이 큰 TypeScript API 목록을 별도로 열거·복사하던 시작 비용을 제거하며,
실제 API 객체와 패키지는 그대로 사용한다. 프로젝트 실행 모듈, 외부 패키지, CommonJS
`require`는 이 빌드 플러그인의 대상이 아니다. 새로운 named import는 잘못된 값을 반환하는
대신 빌드 오류로 드러난다.

브라우저 프리뷰와 vendor 청크는 공백만 축소한다. 식별자·구문 축소와 production 모드
전환은 하지 않아 React 함수명, 개발 진단, JSX 소스 위치와 초기화 순서를 유지한다.
vendor 빌드 스키마는 7, entry 전략은 2로 갱신했다. 이전 학습 모델이나 사용자 설정을
지우지 않으며, setup 완료 전 대상 모듈을 실행하거나 성공 판정 조건을 줄이지 않는다.

| 첫 compiler progress 수신        |    903.0ms |    421.6ms | 53.3% |
| 동일 워커에서 편집 스냅샷 재준비 |    493.8ms |    384.1ms | 22.2% |
| 문서 탐색부터 대상 첫 DOM commit |    346.3ms |    294.9ms | 14.8% |
| 전달 JavaScript 전체             | 3,168,590B | 2,542,760B | 19.8% |

첫 DOM commit은 target의 layout effect에서 기록한다. 브라우저 프로세스 시작 시간,
Inspector 전체 안정화, 복잡한 페이지의 비동기 데이터 완료·자동 복구 완료를 뜻하지 않는다.
첫 compiler progress도 TypeScript만의 순수 실행 시간이 아니라 worker 시작과 요청 처리를
포함한다. 순차 측정이며 시스템 부하·디스크/OS 캐시 차이에 민감하다. 실제 프로젝트에서
동일한 감소율을 보장하지 않는다. 위 fixture의 vendor 청크는 0개이며, 공유 패키지 청크
로딩은 별도의 실제 Chromium 회귀 검사에서 검증했다.

벤치마크는 기존 `dist/previewCompilerWorker.js`를 그대로 사용한다. 측정할 버전의 production
빌드를 준비한 뒤 다음과 같이 실행한다. 출력 파일은 기존 내용을 덮어쓰지 않는다.

```sh
node scripts/benchmark-preview-loading.mjs --samples 7 --browser
```

`--mode component`, `--worker <기존 배포 워커 경로>`, `--output <새 JSON 경로>`도 지원한다.
브라우저를 생략하면 준비와 재준비만 측정한다. fixture·worker·브라우저·서버는 종료 시
정리하며 편집 검사는 실제 소스 파일을 바꾸지 않는 요청 스냅샷으로 수행한다.

## 회귀 검증과 남은 제한

- 40개 기본 import가 TypeScript API를 한 번만 열거하며 실제 AST 생성 결과는 동일함을 검증.
- 공백 축소 전후 함수명·문자열·setup 순서·JSX 소스 위치와 개발 진단을 비교.
- 공백 축소 전후 실제 사전학습 선택, 실패 후 대안, 저장 모델 갱신 결과가 동일함을 검증.
- component와 page-inspector 모드의 revision 1 시작, 공유 vendor 청크 3개 이상 로딩,
  setup 실패와 수정 후 재시작을 실제 Chromium으로 검증. CSP·필수 산출물 오류는 없었음.
- 범위 확장 회귀 177건 중 172건 통과. 나머지 5건은 공백 축소를 비활성화한 대조 실행에서도
  동일하게 실패: 기존 progress 배열 기대값, 동적 자원 dependency 기대값, fast Storybook
  watch dependency 기대값, inventory worker 종료 타이머 검사 2건. 이번 작업에서 변경하지 않음.
- `npm run check`는 기존 51개 파일의 1,000줄 제한 위반으로 중단됨. 변경 전 vendor builder의
  기존 ESLint 오류 20건도 별도로 재현했으며, 새 코드와 나머지 수정 범위 lint는 통과.
- 실제 VS Code 창 재로드나 사용자 페이지의 화면·반응형 시각 검증을 수행한 결과는 아님.
