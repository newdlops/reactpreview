# 프리뷰 판정·경로 탐색·생성 데이터와 실제 상호작용

## 변경

- VCM에서 실제 페이지·대상 출력이 유지돼도 생성 데이터가 정리되며 계약 지문이 바뀌면
  실패로 판정되던 문제를 수정한다. 같은 실행 소유권에서 새 계약을 다시 세 번 관찰한다.
  실제 출력 소실·blocker·불완전 문맥과 사용자 변경·오래된 콜백은 여전히 성공 근거가 아니다.
- 부분 경로의 복구 레시피로 이미 검증한 전체 페이지를 다시 검사하지 않는다. 같은 입력에서
  잠깐 빠졌다가 다시 등록된 과거 후보 기록은 복구하되 현재 문서의 출력은 다시 검증한다.
  모든 후보를 검사했고 현재 출력이 독립적으로 검증됐으면 추가 복원 빌드를 생략한다.
  현재 출력이 사라지거나 일시 상태가 고정돼 있으면 과거의 안정된 실행 계약 복원을 유지한다.
- 소스 근거가 있는 사용자 상태 대기는 실패로 학습하지 않고 다른 후보로 진행한다.
  수동 경로 선택·Auto 끄기·사용자 제어 변경을 우선하며 원본 앱 상태를 강제로 열지 않는다.
- 비동기 출력이나 준비된 페이지가 실제 대상 호스트를 교체하면 새 호스트에도 화면 이동을
  한 번 허용한다. 없는 호스트를 관찰한 것만으로 이동 기회를 소모하지 않는다. 약한 참조로
  해제된 DOM을 보관하지 않으며 사용자 제어 변경·오래된 번들·교체된 타이머는 개입하지 않는다.
- 같은 길이의 REST 경로는 리터럴 세그먼트가 많은 선언을 우선한다. `/api/contents/recent`
  목록을 `/api/contents/*` 상세 타입이 덮어쓰지 않으며 같은 구체성의 최신 선언은 우선한다.
- JSX 키와 표시 용도가 함께 증명된 생성 문자열만 번호를 붙여 독립 표본으로 만든다.
  원본·사용자 JSON·고정 비교값·타입이 선언된 항목·GraphQL discriminator는 바꾸지 않는다.
- 명시적 값 import는 렉시컬 검사기를 만들기 전에 제외하고, 실제 값 참조가 있을 때만
  검사기를 만든다. 진짜 미해결 이름·타입 전용 import·ambient 선언은 기존 검증을 거친다.
- CSS의 HTTPS 수동 리소스 URL을 컴파일 중 파일로 읽지 않고 기존 웹뷰 CSP에 맡긴다.
  JavaScript의 외부 asset import와 자격증명 URL·로컬 경계 검사는 유지한다.
- JavaScript WAV asset URL은 Chromium이 읽을 수 있는 `audio/wav`로 생성한다.
  원본 문자열·명시적 raw import·CSS 로더·파일별 및 전체 asset 크기 한도는 유지한다.

## 성능과 보존 범위

후보 v12를 0.1.1696과 같은 보관 입력·동일한 네이티브 의존성·4GiB 워커로 세 프로젝트를 각각
AB/BA/AB 비교했다. 새 워커와 같은 워커 재준비를 합해 36회이며 모든 쌍의 의존성·CSS·
컨텍스트 범위·진단이 같다. 단계당 120초·즉시 취소·메모리 보호와 원본 읽기 전용을 유지한다.

| 후보 v12의 번들링 중앙값 | 첫 준비 | 재준비 |
| ------------------------ | ------: | -----: |
| VCM                      |  -27.2% | +50.9% |
| 세금 표                  |  -37.3% | -32.1% |
| UDT                      |  -69.6% | -50.1% |

이 수치는 CPU 샘플링을 끈 실제 준비 시간이며 실행 중 시스템 부하와 메모리 압축이 컸다.
VCM 재번들링은 3.05→4.60초로 증가했다. UDT 컨텍스트 탐색도 첫 준비 0.77→2.41초,
재준비 0.68→1.07초로 증가했다. 모든 원시 측정과 회귀·이상값을 보존하며 전체 프로젝트에서
항상 빨라졌다고 주장하지 않는다. 실제 UDT 자동 실행의 후속 빌드 16→1회 감소와 구분한다.
설명용 JSDoc 분석을 줄이는 별도 실험은 일관된 이득이 없어 제품 변경에서 제외했다.

## 검증 상태

- 전체 `npm run check`: 733개 파일, 5,753개 테스트와 빌드 통과.
- 설치한 최종 번들의 VCM·세금 표는 후속 빌드 없이 ready, UDT 상세 화면은 후속 빌드 1회 후 ready.
  VCM의 지속 상태는 verified, 회귀 수 0이며 실제 출력과 전체 페이지 문맥을 확인했다.
- 같은 파일의 7개 서로 다른 경로와 복귀 8회가 ready다. 상세 화면의 5개 부모 경로와 복귀를
  새 브라우저에서 두 번 반복해 12회 모두 ready·실제 출력·blocker 없음으로 확인했다.
  초기 후보의 두 경로 대기는 상세 DOM이 내부 스크롤 아래에 가려진 실행에서 재현했다.
  저장된 수정 전 코드와 현재 코드를 실제 브라우저의 호스트 교체로 비교하면, 이전 코드는
  새 컨테이너의 scrollTop 0에서 대상을 가리고 현재 코드는 220으로 이동해 대상을 드러낸다.
  초기 부분 출력은 성공으로 세지 않는다. 이 수정과 실제 REST 목록 타입 우선순위를 포함한
  후보 v12를 전체 검사·production 패키징·정확한 설치 바이트 확인까지 마쳤다.
- 브라우저에서 실제 Provider의 anonymous/member/admin/anonymous 분기와 관리자 버튼 권한,
  모달 두 번 개폐·한글 입력·Tab·Esc·포커스 복원·Enter 재열기를 확인했다.
  로컬 SVG·공개 HTTPS 이미지·실제 외부 font face·WAV readyState 4를 확인했다.
  390×844, 768×1024, 1440×900 캡처를 각각 시각 검사했다.
- darwin-arm64 production VSIX의 런타임 2,461개 파일·네이티브 바이너리·제외 파일을 검증하고
  정확한 VSIX로 0.1.1697을 로컬 설치했다. 설치 바이트가 패키지와 같고 설정·학습 파일 9개를
  설치 직후 해시 및 모드로 대조해 보존을 확인했다.
- 설치 후 전용 VS Code 창을 다시 로드하고 실제 웹뷰에서 로그인·권한 분기와 모달 두 번 개폐,
  한글 입력·Tab·Esc·포커스 복원·Enter를 조작했다. Inspector의 Page ready와 Console (0)을
  확인했다. 후속 창 검증에서는 1716×932 네이티브 창의 실제 프리뷰·Inspector·이미지와 모달을
  시각 검사했다. 앞선 검은 웹뷰 캡처 현상은 재현되지 않았다. 로그인·권한 분기와 키보드 동작을
  다시 검사하고 재마운트 후 Page ready·Console (0)·초기 상태 복원을 확인했다.
  후보 v12의 재설치 뒤 전용 창을 다시 로드하고 Page Context를 새로 열어 같은 상호작용을
  다시 확인했다. 실제 네이티브 화면·모달을 시각 검사했고 Page ready·Console (0)·편집기
  No Problems를 확인했다. 확장 활성화 시각이 이번 설치 뒤이며 설치된 worker 해시는 후보와 같다.

인증 범위는 사용자가 선택한 프리뷰 내부 로그인·권한 분기다. 외부 서비스 로그인은 수행하지
않았다. 원본 프로젝트·시스템 설정·CSP·권한·VPN 정책은 변경하지 않았다.
기존 CSP의 `frame-src 'none'`으로 차단되는 외부 영상 iframe은 일부 UDT 화면에 표시되지 않는다.
허용된 이미지·폰트·로컬 미디어 검증과 구분하며 이를 위해 CSP를 완화하지 않는다.
