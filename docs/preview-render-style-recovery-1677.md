# 렌더링·스타일 복구와 준비 비용 — 0.1.1677

이 변경은 기존 페이지의 실행과 스타일을 보존하면서 실패 복구와 준비 비용을 개선한다.
실제 목적지 대신 redirect 안내만 나타난 경우, 대상이 없는 페이지, 상위 페이지 오류는
성공으로 세지 않는다. 컴파일 완료 시간과 브라우저의 대상 렌더링 성공은 별도로 검사한다.

## 실행 값 보존

자동 resolver props와 성공 checkpoint는 JSON 왕복 대신 제한된 런타임 복사를 사용한다.
React element는 불변 값으로 보존하며 내부 owner 그래프를 순회하지 않는다. 변경 감지는
element 종류·type·key·props를 사용한다. 콜백·정규식·날짜·배열을 유지하고, 지원하지 않는
접근자·객체는 기존 상태를 훼손하지 않도록 거절한다. JSON 편집기의 의미는 바꾸지 않는다.

한 props 경로를 수정할 때 해당 일반 객체 경로만 복사한다. 다른 자식·긴 배열·함수는
동일성을 유지하고, prototype 경로나 class 내부 필드·접근자를 임의로 수정하지 않는다.
자동 보완은 자동 학습의 사용자 제어·reachability 검사를 그대로 통과해야 한다.

## Next App Router

새 Page Execution 경로에도 기존 Next 제어 신호 경계를 적용한다. 브랜드가 일치하는
redirect·notFound·forbidden·unauthorized만 제어 신호로 읽고, 일반 오류는 기존 경계에 맡긴다.
현재 제어 안내가 남은 화면은 headless 성공 판정과 성공 학습에서 제외한다.

첫 실행문에서 `next/navigation`의 redirect를 리터럴 로컬 경로로 호출하는 경우에만
기존 파일시스템 route 목록에서 유일한 목적지를 찾는다. 최초 목적지와 최대 4회 전이를
사용하고 외부 URL·동적 값·조건부 호출·모호한 경로는 자동 선택하지 않는다. 선택이 없는
레이아웃 미리보기는 확인된 최종 페이지를 먼저 준비해 불필요한 재번들을 피한다.
명시적인 수동 페이지 선택은 우선하며, redirect 전용 페이지는 자동 탐색에서 반복하지 않는다.
기존 호스트의 실행 후보 예산과 문서 교체 시 입력 식별자 검증도 유지한다.
구문 오류나 로컬 재정의로 import 바인딩이 가려지는 페이지도 자동 목적지 증거로 사용하지 않는다.

## 로컬 UI와 Tailwind

frozen 실행 그래프에서도 순수한 React 상태·ref·이벤트 콜백으로 확인한 작은 로컬 훅은
일반 모듈 예산 안에서 보존한다. 모듈당 32KiB, 요청당 최대 64개·증거 텍스트 1MiB다.
타입 전용 import는 허용하지만 backend 호출·효과·알 수 없는 실행은 이 증거로 허용하지 않는다.
실제 계정 메뉴의 초기 닫힘, 마우스 열기, Escape 닫기를 별도로 검증한다.

초기 스타일 그래프 128개와 최종 corridor 512개의 소스를 함께 수용하도록 스냅샷 파일
한도를 640개로 맞춘다. 전체 텍스트 4MiB, inline 후보 8,192개·256KiB는 그대로다.
선택한 소스를 먼저 처리하고, 생성된 타입 식별자보다 JSX·TSX·HTML·Vue·Svelte·MDX의
클래스를 먼저 수집한다. 후보 한도에 도달하면 추가 스캐너 호출을 하지 않는다.

프로필 페이지의 수정 전후 CSS 구조 비교에서는 기존 규칙·선언이 제거되지 않았고,
빠졌던 제목 크기·정렬·반응형 유틸리티가 복구됐다. CSS는 4,054,128→4,072,119바이트로
17,991바이트 증가했다. 이 값은 소스 변경에 따른 별도 비교이며 브라우저 캐시 크기는 아니다.

## 준비 비용

변환기의 private AST를 같은 경로·같은 텍스트인 경우에만 hook·guard 분석에 공유한다.
체커가 소유한 AST나 다른 텍스트의 노드는 공유하지 않는다. 이미 다른 변환이 차지한 guard
읽기에는 불필요한 타입 조회를 하지 않는다. 소스 후보 경로의 정규화·토큰화도 실제 역방향
탐색이 필요할 때 수행한다. 후보 순서·분석 범위·입력 변경 검사는 유지한다.

고정한 실제 프로젝트 입력에서 기존 0.1.1676과 production 설정의 수정 워커를 직렬로
비교한다. 브라우저는 CDP pipe와 제한된 Fetch 응답을 사용하며 TCP 포트·개발 서버를 열지
않는다. 실제 제품의 selection controller·실행 후보 예산·문서 교체 식별자를 사용한다.
렌더링·계산 스타일·390×844, 768×1024, 1440×900 화면은 컴파일 검사와 별도로 확인한다.

큰 모달의 첫 재현 도구가 호스트 예산과 입력 식별자를 누락한 결과는 최종 성공 근거에서
제외한다. 동일 호스트 로직으로 다시 검사하며, 남은 상위 문맥 오류와 데이터 일관성 문제를
부분 성공 또는 실패로 기록한다. 이를 완전한 페이지 성공으로 바꾸는 예외는 추가하지 않는다.

## 자원·설치·제한

제품 호스트 로직으로 비교한 6개 입력 중 완전한 대상 렌더링은 기존 3개에서 4개로 늘었다.
Next 프로필 목적지가 새로 성공했고, 대출 목록·투자 입력 폼·삭제 확인 모달의 성공은 유지했다.
큰 과세 모달은 양쪽 모두 `partial-blocked`, 세금 표는 상위 문맥 오류 때문에 양쪽 모두
`post-commit-failed`로 남았다. 표나 레이아웃이 보인다는 이유로 완전 성공으로 세지 않았다.

첫 준비의 직렬 비교에는 다음처럼 개선과 지연이 함께 있었다. 단위는 ms이며
레이아웃은 실제 목적지의 실행 범위가 달라 동일 출력의 속도 비교에서 제외한다.

| 입력           | 컨텍스트 기존→수정 | 번들링 기존→수정 |
| -------------- | -----------------: | ---------------: |
| 대출 목록      |              41→43 |    14,051→10,591 |
| 투자 입력 폼   |        3,693→7,407 |      5,857→6,438 |
| 삭제 확인 모달 |        2,277→2,623 |      7,585→7,223 |
| 과세 모달      |        6,011→6,599 |    18,499→19,029 |
| 세금 표        |        3,834→3,181 |    16,727→16,122 |

투자 입력 폼의 추가 비교에서는 컨텍스트 2,274→2,073ms, 번들링 6,360→5,761ms,
Node CPU 16,198→14,156ms였다. 실행 간 편차가 크므로 전반적인 속도 개선을 확정하지 않는다.

자원 증가는 실제 UI 복구에 필요한 범위에서 측정한다. 기존 텍스트·생성 후보·실행 그래프·
워커 한도를 유지하고, 종료한 자체 진단 프로필은 정확한 경로별 보존 검사 후 정리한다.
원본 프로젝트·설정·학습 데이터는 정리 대상으로 삼지 않는다.

과세 모달 연속 복구에서 초기 합산 RSS 진단 한도 3.5GiB에 수정 버전이 걸린 실패도 보존한다.
당시 기존→수정 피크는 3,526→3,657MiB였다. Node 3GiB·네이티브 1GiB 개별 진단 한도는
유지하고 두 한도의 합계 4GiB를 양쪽에 똑같이 적용한 재검사에서는 3,756→3,663MiB였다.
이는 1초 간격으로 측정한 컴파일러 프로세스와 네이티브 자식의 RSS이며 브라우저는 포함하지 않는다.
제품의 메모리 설정은 바꾸지 않았고, 약 4% 이내의 변동을 전체 메모리 증가로 일반화하지 않는다.

대출 목록 CSS는 이전의 `.static`·`.resize` 두 선택자를 제외하고 기존 규칙을 보존했다.
실제 UI 소스 우선 수집으로 22개 선택자가 추가됐으며, 세 크기의 계산 스타일·라디오 이동·
검색 입력을 확인한다. 프로필 CSS의 기존 규칙·선언 순서는 모두 보존됐다.
최종 대출 화면에서 빠진 두 선택자와 일치하는 DOM은 세 크기 모두 0개였다.

최종 검증은 전체 `npm run check`, 변경 범위 회귀 검사, production VSIX 검사와 정확한
로컬 설치 파일 비교를 포함한다. 이 환경의 전용 루프백 `127.1.0.1`을 바인딩하는 기존
headless 검사 10개는 `EADDRNOTAVAIL`로 실패하며 시스템 네트워크 설정을 변경하지 않는다.
실제 페이지 검증은 포트가 필요 없는 별도 경로로 수행한다.

최종 `npm run check`는 타입·린트·포맷·줄 수 검사를 통과하고 테스트 5,412개 통과,
기존 루프백 실패 10개를 기록했다. production 빌드와 darwin-arm64 VSIX 검사는 통과했다.
0.1.1677 로컬 재설치 후 런타임 2,461개 파일이 패키지와 일치하고, 설정·학습 파일 9개의
바이트와 권한이 보존됨을 확인했다. 최종 워커에서 성공한 네 화면의 마우스·키보드 입력과
세 크기를 다시 검사했다. VS Code 창 재로드는 수행하지 않았다.
자체 브라우저 프로필 44개와 압축 보관한 진단 SDK를 정리해 순 논리 용량 1,378,569,103바이트를
회수했다. 전반적인 준비 속도와 남은 두 화면의 문맥 오류는 계속 분석할 항목이다.
