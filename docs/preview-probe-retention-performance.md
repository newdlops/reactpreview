# 반복 소스 검사 캐시의 보관 범위

0.1.1671은 순수 런타임 계측 판정의 항목 한도를 128개에서 512개로 조정한다.
기존 전체 데이터 1MiB와 소스당 65,536 UTF-16 코드 단위 한도는 유지한다. 저장 내용은 경로·정확한 원문·
boolean 판정이며 AST나 파일시스템 조회 결과는 아니다. 경로나 원문이 달라지면 다시 검사한다.

## 확인한 반복 작업

고정 IR 페이지는 최초와 재요청 모두 455개 소스를 검사했다. 기존 항목 한도는 128개여서
1MiB 용량을 남겨 두고도 결과가 계속 밀려났고, 재요청 적중이 0건이었다.
원래 진단의 실제 검사 시간 합계는 약 100ms였다. 이는 준비 단계 전체 소요 시간이 아니다.

같은 생산 코드에 scalar 계수기만 추가해 두 정책을 각각 최초·재요청했다.
입력 원문 SHA-256·검사 판정·CSS·의존성·진단·페이지 문맥·감시 경로가 네 요청 모두 같았다.

| 정책            | 최초 검사 | 재요청 적중 | 재요청 검사 | 관측 최대 데이터 |
| --------------- | --------: | ----------: | ----------: | ---------------: |
| 기존 128개/1MiB |       455 |           0 |         455 |         373,774B |
| 후보 512개/1MiB |       455 |         455 |           0 |         781,398B |

소스 내용 변경 시 기존 무효화 절차를 그대로 적용한다. 판정이 true이면 실제 변환은 매번
현재 준비 옵션으로 수행한다. 준비 문맥·스타일·타입·그래프·출력 한도는 변경하지 않는다.
Node 4GiB, 네이티브 2개 슬롯·256MiB, Sass 512MiB·30초와 15초 유휴 종료도 유지한다.
새 의존성·디스크 캐시·상주 서비스·시스템 설정 변경은 없다.

## 기능과 화면 검증 범위

고정 VCM 복사본의 네 대상을 AB/BA 순서로 최초·재요청하여 실제 브라우저 32회를 검증했다.
타깃 마운트·출력·필수 리소스·문서 종료와 짝별 CSS·의존성·진단·선택 문맥·감시 경로를
확인했다. 전체 TypeScript 카탈로그와 같은 프로젝트 내부 의존성 저장소를 사용했다.
adapter-learning root는 양쪽 모두 생략했으며 원본 프로젝트와 사용자 저장소는 수정하지 않았다.

실제 GP 페이지를 1440×900, 768×1024, 390×844에서 확인했다. 정상 Tab·초대·취소와
캐시 갱신 2회를 실행하고 PNG 12개를 실제로 열어 기준 화면과 비교했다. 작성된 CSS와
계산 스타일을 비교했다. 서버는 127.1.0.1 루프백, 브라우저 제어는 CDP 파이프다.

이 수정은 반복 검사 약 100ms의 원인을 줄이는 변경이다. 1분 대기 전체의 개선율을
입증한 수치는 아니다. 전체 로딩 시간은 기록만 했고 속도 개선 주장이나 채택 기준으로
사용하지 않았다. 이전 자원 확대·AST 공유·문서 투영 후보는 탈락 결과를 유지하고 적용하지 않았다.
