# 타입 값 합성의 중복 계산 감소 — 0.1.1705

프리뷰 준비 중 타입으로 표본 값을 만드는 과정에서, `null`로 반환할 항목이나 실질 후보가
하나인 nullable 항목도 선언 순서 분석과 정렬을 수행했습니다. 여러 후보를 정렬할 때에는
같은 타입의 요구 충족 점수와 정렬 키를 비교할 때마다 다시 계산했습니다.

## 변경과 보존 조건

- 기존 규칙상 `null`인 오류·fallback·종료 시각 항목은 정렬 전에 반환합니다.
- nullish 멤버를 먼저 제외하고 남은 후보가 0개·1개이면 순서 분석을 생략합니다.
  리터럴 후보가 하나여도 기존 허용 리터럴 목록은 기록합니다.
- 여러 후보의 요구 충족 점수는 한 번씩 계산합니다. 같은 점수의 선언 순서와, 첫 후보를
  합성할 수 없을 때 다음 후보를 시도하는 동작을 보존합니다.
- 문자열 정렬 키는 해당 유니온 정렬 안에서만 재사용합니다. 프로그램이나 다음 합성에
  타입·점수를 보관하지 않아 새로운 요구 경로에 이전 순위가 섞이지 않습니다.
- 깊이 9·노드 1,200개·리터럴 목록 16개·목록 길이 상한과 날짜·상태 선택 규칙을
  유지합니다. 경로 탐색, 후속 빌드 한도, CSS·테마·Provider와 시간 제한은 변경하지 않습니다.

## 실제 프로젝트 검사

검색 페이지와 제보된 VCM PFC 목록 파일을 이전·수정 컴파일러로 최초 준비·재준비했습니다.
계측은 검증 전용 컴파일러에만 추가했고 설치 번들에는 포함하지 않습니다.

| 대상         | 합성 결과 |   정렬 키 계산 | 후보 점수 계산 |
| ------------ | --------: | -------------: | -------------: |
| 검색 페이지  |       353 | 10,838 → 1,602 |  3,802 → 1,826 |
| VCM PFC 목록 |        65 |      558 → 145 |    1,360 → 295 |

최초·재준비 모두 합성 값, 허용 리터럴, 노드 수와 객체 키 순서가 일치했습니다. 검색
의존성 3,845개·VCM 2,791개, 소스 지문, 문맥, 감시 경로와 CSS도 일치했습니다.

TypeScript가 표시하는 `typeText` 설명 문자열은 재준비에서 7곳의 속성·키 유니온 순서가
달랐습니다. 전체 결과의 차이를 보관한 뒤, 실제 합성 값과 리터럴의 직렬화 바이트를 별도로
비교하여 이 표시 문자열 외의 차이가 없음을 확인했습니다. 모든 JavaScript 청크의 바이트가
같다고 주장하지 않습니다. 검색 페이지에는 기존 프레임워크·서버 계약 경고가 있으며,
계측 재준비에서 출력 개수는 0→1이었지만 새 경고 종류와 오류는 없었습니다.

## 합성 함수만의 제한된 측정

같은 가상 TypeScript 프로그램에서 예열 8회 뒤, 이전·수정 함수를 교대로 16표본씩 측정했습니다.
표본마다 8회 합성했으며 프로그램 생성·파일 읽기·번들링은 측정에 포함하지 않았습니다.
모든 표본의 전체 합성 결과가 이전과 같았습니다.

| 사례                    | 이전 중앙값 | 수정 중앙값 |
| ----------------------- | ----------: | ----------: |
| nullable 레코드         |      0.66ms |      0.58ms |
| 성공 시 비어 있는 필드  |      0.93ms |      0.41ms |
| 요구 경로가 있는 유니온 |      0.75ms |      0.57ms |
| 선언된 리터럴 목록      |      1.19ms |      1.00ms |

이 수치는 합성 함수의 제한된 비용이며 전체 프리뷰 속도 향상을 보장하는 수치는 아닙니다.

계측 없는 준비 검사는 최초 비교 8회와 순서를 바꾼 비교 16회를 포함합니다. 최초 검색
비교에서는 7.12→11.40초로 느린 표본도 나왔습니다. 순서 교대 검사에서 각 2표본의
중앙값은 다음과 같았습니다. VCM 재준비가 느린 결과도 있어 전체 속도 향상을 확정하지 않습니다.

| 교대 검사 대상 | 이전 중앙값 | 수정 중앙값 |
| -------------- | ----------: | ----------: |
| 검색 최초 준비 |     10.60초 |      5.72초 |
| 검색 재준비    |      6.75초 |      4.77초 |
| VCM 최초 준비  |      9.98초 |      7.47초 |
| VCM 재준비     |      4.42초 |      5.24초 |

최초 비교의 Node와 네이티브 자식 합산 최고 RSS는 검색 1,922→1,972MiB,
VCM 1,779→1,792MiB였습니다. 이 제한된 검사에서의 차이이며 일반적인 메모리 감소를
의미하지 않습니다. 측정용 워커 한도와 제품의 메모리 한도는 변경하지 않았습니다.

영구 회귀검사는 기본값과 메타데이터, 선언 순서·enum·동점, 요구별 재평가, 합성 불가 후보의
다음 시도와 재귀 예산을 포함합니다. 전체 검사·production VSIX·설치 파일 일치 결과는
아래 검증 기록에 보관합니다.

자식 프로세스의 종료를 확인하며, 기존 설정·학습 기록을 보존합니다. 이번 작업에서 네이티브
