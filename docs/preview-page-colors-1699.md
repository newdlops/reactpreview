# 원본 페이지의 밝음·어두움 색상 보존

ZUZU Roundup의 `src/app/(public)/search/page.tsx`에서 다크 테마의 토큰과 일부 패널은
어두운 색인데 본문은 흰 배경·검은 글자로 남는 증상을 재현했다. 원본의 `globals.css`는
`@layer base`에서 본문 배경·글자색을 지정한다. 프리뷰의 계층 없는 기본색 규칙이 이보다
우선했고, 낮은 selector specificity만으로는 이를 막지 못했다.

프리뷰의 기본색과 `color-scheme`을 별도 `react-preview-defaults` 레이어에 둔다.
이후 로드되는 원본의 CSS 레이어와 일반 CSS가 우선한다. 편집기의 기본 레이어가 있는 경우도
검사하며, 스타일 없는 페이지는 기존의 흰 배경·검은 글자를 유지한다. 로딩·오류·Inspector
표시와 기존 CSP는 유지한다. 컴파일·경로 선택·후속 빌드·번들 CSS에는 변경이 없다.

원본 프로젝트는 읽기만 하고, 고정 사본과 동일한 컴파일 결과로 수정 전·후 HTML을 비교한다.
외부 인증·DB·검색 서비스의 실제 응답은 이 색상 검증 범위에 포함하지 않는다.

같은 컴파일 결과를 고정하고 호스트 HTML만 전후 비교했다. 수정 전 다크 테마는 본문이
`rgb(17, 17, 17)` / `rgb(255, 255, 255)`였다. 수정 후에는 원본의 `--foreground` /
`--background`와 같은 `oklch(0.985 0.0095 248)` / `oklch(0.145 0 0)`였다. 라이트 모드도
원본 토큰과 일치하며, 두 테마의 390·768·1440px 화면을 실제로 시각 검사했다.

밝음→어두움→편집기 테마 변경→밝음 복귀, 일반 CSS와 스타일 없는 페이지를 실제 Chromium의
계산 색상으로 회귀 검사한다. 원본 앱의 포인터 테마 전환은 초기 검사에서 클래스 변경을
확인하지 못했으므로 성공 검증으로 집계하지 않는다. 실제 페이지의 색상 비교는 독립된 새
문서에 원본의 저장 테마 선호를 설정해 수행했다.

검증 결과는 `.tmp/preview-search-colors-1699-20261026t1817z/`에 보관한다. 원본 소스
2,436개의 해시·권한과 폰트 97개의 해시가 유지됨을 확인했다. 사용이 끝난 검증 프로필 6개를
정리했고, 입력 사본은 해시를 확인한 `immutable-inputs.tar.gz`로 압축 보관했다.

`npm run check`는 735개 파일·5,763개 테스트를 포함해 통과했다. production 빌드와
darwin-arm64 VSIX를 검증하고 0.1.1699를 로컬 설치했다. 설치된 런타임 2,461개 파일은
패키지와 일치하며, 이전 버전과 다른 런타임은 호스트 HTML을 생성하는 `extension.mjs` 하나다.
컴파일 워커·의존성은 동일하다. 기존 설정·학습 파일 9개의 내용과 권한도 보존됐다.
사용 중이던 기존 VS Code 창은 `Developer: Reload Window` 후 프리뷰를 다시 열어 적용한다.
