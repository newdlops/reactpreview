# 0.1.1710 과거 임원 패널 준비와 렌더링

대상은 payroll 프로젝트의 `previous-directors-panel.tsx`입니다. 원본 파일이나 프로젝트 설정을
변경하지 않고 프리뷰의 정적 변환과 타입 질문을 수정했습니다.

## 원인과 변경

실제 VS Code 로그와 기존 번들의 격리 Chromium 실행에서 회사 공통 셸 `CompanyCmdk`의
`Cannot access 'topResultLabel' before initialization` 예외를 재현했습니다. 원본은
`useMenuGuides(open)` 호출 뒤 `topResultLabel`을 선언하고, 그 뒤에 `menuGuides?.[topResultLabel]`을
읽습니다. 프리뷰 변환기가 이를 hook 호출 시점의 대체 객체 키로 옮겨 초기화 순서를 깨뜨렸습니다.

계산 키를 유지하기 전에 같은 함수의 선언과 어휘 범위를 확인합니다. 매개변수와 먼저 초기화된
가시 지역 변수는 유지하고, 이후 선언·다른 블록·모호한 중복 선언은 대체 객체에 넣지 않습니다.
함수별 구문 카탈로그는 WeakMap으로 공유하고 8,192개 노드를 넘으면 보수적으로 중단합니다.
기존 모듈/외부 키 정책과 원본 hook 반환값, 계산 키 8개 한도는 유지합니다.
관련 없는 객체의 인덱스 접근에는 이 선언 확인을 수행하지 않습니다.

CPU 표본에서는 GraphQL 문서 후보의 타입 질문이 styled-components 템플릿의 제네릭 호출 추론까지
유발했습니다. 명시적 타입이 없는 템플릿이 실제 `styled-components`/`@emotion/styled` import에
연결될 때만 문서 타입 질문을 생략합니다. 별칭 import를 확인하고 이름만 같은 지역 함수는
제외하지 않습니다. 명시적 타입·형 변환·알 수 없는 태그는 기존 구조적 분석을 유지합니다.
스타일 코드 자체와 번들 도달 범위는 삭제하지 않습니다.

## 준비 비용

같은 워커 빌드 옵션으로 기존/수정본을 교대 실행했습니다. 각 워커의 첫 준비와 같은 입력의
반복 준비를 한 번씩 측정했습니다. 단위는 초이며 값은 반올림했습니다.

| 실행        | 기존 전체 | 수정 전체 | 기존 번들 구간 | 수정 번들 구간 |
| ----------- | --------: | --------: | -------------: | -------------: |
| A 첫 준비   |     34.36 |     42.17 |          24.67 |          21.28 |
| A 반복 준비 |     27.39 |     17.58 |          20.34 |          13.03 |
| B 첫 준비   |     23.43 |     16.37 |          15.91 |          11.29 |
| B 반복 준비 |     14.43 |     14.17 |          11.19 |           9.99 |

번들 구간 중앙값은 18.12→12.16초로 약 33% 줄었습니다. 각 구간은 번들링 진행 신호부터
워커 응답까지입니다. 네 관측 모두 의존성 2,463개와 순서, CSS 해시가 같았고 출력은
11,292,874→11,292,860바이트였습니다. 호스트 부하에 따른 편차가 크고 A 첫 준비는 전체 시간이
늘었으므로 컨텍스트 탐색이나 전체 준비 시간의 일관된 단축을 보장하지 않습니다.

별도 CPU 표본에서 문서 shape 수집의 누적 표본 시간은 2,141→658ms,
태그 템플릿 호출 해석은 2,405→980ms였습니다. 이는 각 한 번의 프로파일 관측이며
다른 함수와 중첩되는 값으로, 전체 시간 절감량에 더하지 않습니다.

## 실제 입력 검증

초기화 순서 수정본에서 원래 회사 페이지의 `/company/1/directors` 경로를 실행했습니다.
`PreviousDirectorsPanel`의 실제 마운트 1개, 대상 출력, `page-authentic`, 탐색 1회·`reached`,
활성 차단 0개, 처리되지 않은 예외 0개를 확인했습니다. 최종 번들은 1440×1000, 768×1000,
390×1000에서 모두 같은 성공 판정을 받았고 실제 스크린샷을 확인했습니다. ‘과거 임원’ 탭이
선택됐고 빈 목록 안내와 대상 스타일이 표시됐습니다. 실제 계정이나 운영 데이터는 사용하지
않았습니다.

데스크톱에서 Inspector의 기존 props API로 검증 전용 임원 두 행을 넣어 이름·퇴임 사유·날짜와
마스킹 표가 표시되는 것도 확인했습니다. 이 결과를 원래 생성 데이터에 과거 임원이 있다고
해석하지 않습니다. 탭 클릭도 실행했으나 자동 대상 탐색이 ‘과거 임원’으로 돌아왔고 중간 표본은
부분 차단 상태였습니다. 다른 탭의 수동 선택 유지까지 검증 완료했다고 주장하지 않습니다.
작은 화면의 합성된 공통 상단 공지·사용자 문자열은 밀집해 표시되며 이번 수정 범위는 아닙니다.

현재 PortManager 전용 주소 `127.1.0.1`은 네트워크 인터페이스에 없어 일반 TCP 검증이
`EADDRNOTAVAIL`로 실패합니다. 시스템 주소나 정책을 바꾸지 않았습니다. 별도 진단 번들에서
동일한 HTML·아티팩트 처리기를 CDP 파이프로 전달하는 포트 없는 메모리 전송을 사용했습니다.
원본 프로젝트 코드는 격리 Chromium 안에서만 실행했고 외부 요청은 차단했습니다.
이 검사는 일반 TCP 전송이나 실제 VS Code 창 검증을 완료했다는 뜻이 아닙니다.

## 회귀 검사와 설치

초기화 전 키·블록 밖 키를 실행하는 합성 회귀는 수정 전 2개 실패를 재현했고 수정 후
5개가 통과했습니다. 가시 키의 배열 계약과 원본 값을 보존합니다. 스타일 import 별칭의 불필요한
타입 질문 생략, 명시적 문서 타입·사용자 태그 보존도 검사했습니다. 관련 9개 파일·106개 검사는
통과했습니다.

`npm run check`는 유지 파일 1,868개의 줄 수, 타입, 린트, 포맷을 통과한 뒤 테스트에서
종료 코드 1로 끝났습니다. 테스트 750개 파일 중 744개, 5,899개 항목 중 5,887개가 통과했습니다.
나머지 6개 파일·12개 실패는 `127.1.0.1`의 `EADDRNOTAVAIL`와 그로 인한 실행 전 중단입니다.
0.1.1709의 같은 환경 재검사 기록과 실패 항목이 일치합니다. 전체 검사가 통과했다고
표현하지 않습니다. 기존 사용자 작업 문서의 trailing whitespace도 그대로 보존했습니다.

별도 production prepublish 빌드는 통과했습니다. darwin-arm64 VSIX의 manifest, ARM64 네이티브
esbuild, React 18·19, TypeScript 라이브러리와 런타임 170개 파일을 확인했습니다. 지침·프로젝트
설정·임시 자료는 포함되지 않았습니다. 0.1.1710 로컬 설치 후 전체 payload 2,465개 파일이
설치 메타데이터를 제외하고 검증한 VSIX와 일치했습니다.

설치된 워커로 대상 파일을 다시 준비하고 포트 없는 Chromium에서 `ready`, 실제 대상 마운트 1개,
대상 출력 있음, 활성 차단 0개, 예외 0개를 확인했습니다. 이 설치본의 첫 준비는 30.67초였으며
한 번의 관측입니다. 원본 프로젝트 쓰기 시도는 없었고 실행별 브라우저·프로필은 정리했습니다.
설치 전후 학습 모델·설정·최신 학습 입력·사용자 작업 문서의 해시는 같았습니다.
사용 중인 VS Code 창은 재로드하지 않았으므로 실제 창 적용에는 `Developer: Reload Window`가
필요합니다. 비교용 워커와 검증 의존성 복사본은 정리하고 압축된 검증 근거와 최신 VSIX를 남깁니다.
