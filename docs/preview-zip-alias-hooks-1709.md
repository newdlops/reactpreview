# 0.1.1709 준비 비용과 렌더 변환 보존

Yarn ZIP의 반복 디렉터리 읽기를 줄이고, 실제 별칭 파일과 컬럼 변환 훅이 대체물로 바뀌던
두 경로를 수정했습니다. 원본 프로젝트의 설정·스크립트는 실행하지 않습니다.

## 변경

- 컴파일러의 파일 분석 캐시에 ZIP 디렉터리 메타데이터를 공유합니다. 한도는 아카이브 128개,
  항목 16,384개, 보수적으로 계산한 저장량 8MiB입니다. 소스 바이트와 파일 핸들은 별도로
  소유하며 읽기마다 크기 한도와 아카이브의 전후 동일성을 검사합니다.
- 동시 요청은 필요한 이름을 찾을 때까지 한 디렉터리 탐색을 공유합니다. 캐시 한도로 앞선
  항목이 저장되지 않았다면 늦게 들어온 요청은 처음부터 별도로 탐색해 파일을 놓치지 않습니다.
  오류·삭제·초기화·이전 세대의 늦은 완료가 새 캐시를 복원하지 않습니다.
- ZIP 동일성에 장치·inode·ctime을 포함합니다. 같은 크기와 mtime을 유지한 파일 교체에서도
  이전 텍스트나 디렉터리 오프셋을 재사용하지 않습니다.
- tsconfig 별칭의 가장 구체적인 패턴과 전체 대체 경로를 확인합니다. 뒤쪽의 실제 파일이나
  패키지 디렉터리를 앞쪽 누락 경로의 생성 UI 대체물로 가리지 않습니다. 존재하는 경로는
  추가 상위 경로 정규화 없이 정상 모듈 해석으로 넘기며, 누락 경로의 작업공간 경계는 유지합니다.
- 고정된 번들 범위를 만들 때 원본 훅의 렌더 변환도 포함합니다. 기존 분석기의 구문 트리를
  재사용하며 소스 증명 64개·전체 1MiB·파일당 32KiB 한도는 그대로입니다. 직접 데이터 전달과
  반환값 없는 부수효과 훅은 계속 대체할 수 있습니다.

## 실제 입력 검증

2026-10-30 TADA 예약 페이지에서 ZIP 소스 512개를 읽을 때 디렉터리 항목 방문은
98,800회에서 8,991–9,025회로 줄었습니다. 의존성 1,098개, 감시 경로, CSS 해시,
21,181,392바이트 출력과 진단 수는 수정 전후 같았습니다.

같은 프로젝트의 lodash 소스 252개를 별도로 읽는 교대 검사에서 결과 텍스트의 합산 SHA-256은
모든 실행이 같았습니다. 수정 전 1,345/1,210/1,403ms, 수정 후 377/514/323ms였으며
중앙값 기준 약 72% 감소했습니다. 이 수치는 ZIP 읽기 구간이며 전체 페이지 시간은 아닙니다.

전체 준비 시간은 초기 ZIP 수정 교대 검사에서 10.65→9.27초였으나, 최종 교대 검사에서는
수정 전 10.87/22.21초, 수정 후 13.39/25.73초로 흔들렸습니다. 다른 프로세스 부하도 관측되어
전체 페이지의 확정적인 시간 단축이나 성능 비퇴행을 주장하지 않습니다. 반복 준비 시간도
4.88/5.21초 대 7.80/13.01초로 편차가 컸습니다. 추가 측정이 필요합니다.

최종 수정본의 TADA 예약 페이지와 RTCC 투자자 표는 별도 헤드리스 브라우저에서 `ready`,
대상 출력 있음, 대상 마운트 1개, 활성 차단 0개, 처리되지 않은 예외 0개로 확인했습니다.

RTCC `rtcc-judgment-chip.tsx`는 원본 `useSortColumn`이 빈 훅으로 대체되어,
`setSortColumn`/`applySortStyle` 호출 뒤 컬럼이 undefined가 됐습니다. 원본 훅 보존 후
컬럼의 `type`·그리드의 `children` 접근 예외는 없어졌고 브라우저의 처리되지 않은 예외는
0개였습니다. 의존성은 2,335→2,376개, 출력은 약 170KB 증가했고 준비는 11.62→11.97초였습니다.
이 두 시간은 각각 한 번의 관측입니다.

대상 출력은 20초 관찰에서도 `partial-blocked`였습니다. 데이터·조건 요구 탐색과 실제 VS Code의
후속 후보 재빌드 검증은 남아 있습니다. 성공 판정을 완화하거나 대상이 보인 것으로 기록하지
않았습니다.

검증용 Chromium은 `127.103.218.122` 전용 루프백을 사용했고 각 실행의 브라우저·서버·프로필은
종료·삭제되었습니다. 원본 프로젝트 쓰기 시도는 0건입니다. 사용 중인 VS Code 창 재로드나
수동 화면 검증은 이 기록의 완료 범위가 아닙니다.

## 회귀 검사

ZIP 동시 읽기·용량 제한·파일 교체·포화 후 늦은 요청, 별칭 우선순위·신규 파일 관찰,
원본 훅 보존·데이터/부수효과 경계·증명 한도 검사를 추가했습니다.
`npm run check`가 종료 코드 0으로 통과했습니다. 유지 파일 1,865개의 줄 수, 타입, 린트,
포맷, 테스트 749개 파일·5,892개 항목과 실제 번들을 검사했습니다. 처음 샌드박스 실행은
브라우저 실패·테스트 시간 초과로 중단했으며, Chromium과 루프백 서버 실행 승인을 받은 뒤
동일 명령을 완주했습니다. 검사 기준이나 제한 시간은 변경하지 않았습니다.

production prepublish를 거친 darwin-arm64 VSIX를 생성해 0.1.1709로 로컬 재설치했습니다.
패키지의 런타임 170개 파일이 빌드 결과와 일치하고, 설치된 전체 payload 2,465개 파일도
설치 메타데이터를 제외한 패키지 내용과 일치했습니다. ARM64 네이티브 esbuild와 React 18·19,
TypeScript 표준 라이브러리를 포함하며 프로젝트 지침·로컬 설정·임시 자료는 제외했습니다.

설치본 워커의 컴포넌트 검증에서도 실제 별칭 텍스트의 DOM 출력, 런타임 `ready`, 예외 0개,
브라우저·서버·프로필 정리를 확인했습니다. 이 컴포넌트 모드의 안정화 분류는
`insufficient-evidence`였으며 페이지 경로 성공률 근거에는 포함하지 않았습니다.
학습 모델·최신 학습 입력·사용자 설정·기존 작업 문서의 해시는 작업 전후 같았습니다.
