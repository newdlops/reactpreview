# 0.1.1711 컨텍스트 분석 재사용과 소스 동일성

번들링과 컨텍스트 판단의 결과를 유지하며 반복 정적 분석 비용을 줄였습니다. 원본 프로젝트의
소스·설정·스크립트를 변경하거나 실행하지 않았습니다.

## 변경 근거

payroll 과거 임원 패널의 첫 준비에서 훅 projection 요청은 1,109회였고 기존 캐시 재사용은
204회였습니다. 약 82KiB 공통 메뉴 모듈은 기존 64KiB 개별 제한을 넘어 매번 분석했고,
빈 증명도 반복 계산했습니다. 정확한 빈 결과를 캐시하고 개별 입력 한도를 128KiB로 맞췄습니다.
전체 캐시 한도는 512개·4MiB로 유지합니다. 편집·복원·파서 문법·소스 경로와 전체 용량 제한은
같은 회귀 검사로 확인했습니다. 큰 입력이나 무관한 입력은 계속 전체 증명을 거치거나 제외됩니다.

같은 입력의 두 번째 준비까지 누적 projection 재사용은 582→1,033회였습니다. 첫 준비의
실제 빈 증명 계산은 305→164회였고, 수정본의 두 번째 준비에서는 추가 증명 계산이 없었습니다.
실행 시간이나 렌더 결과를 캐시한 것이 아니며, 소스와 옵션이 바뀌는 판단은 공유하지 않습니다.

React state의 데이터 출처 전파도 동일한 setter 호출을 반복 순회했습니다. AST가 소유하는
WeakMap에 호출 인수 구문만 보관하고 출처 콜백은 매번 호출합니다. state 16개·인수 32개·출처
4개 제한, 중첩 함수의 shadow, optional/spread 호출 제외, import 동일성을 유지합니다.

디스크 소스 캐시는 크기·mtime이 같은 원자 교체와 제자리 수정에서 과거 소스를 반환했습니다.
실제 파일 회귀에서 이를 재현한 뒤 기존 metadata 조회 결과에 device·inode·ctime을 포함했습니다.
파일·import·render 사실은 새 동일성을 관찰하며 추가 stat/read나 원본 프로젝트 쓰기는 없습니다.
파일 시스템이 모든 동일성 정보를 보존하거나 매우 낮은 시간 정밀도를 제공하는 경우까지
내용 해시와 동일한 보장을 한다고 주장하지 않습니다.

## 실제 입력 교대 측정

2026-11-01, 동일한 워커 빌드 옵션으로 기존 A→수정 A→수정 B→기존 B를 순서대로 실행했습니다.
각 워커에서 첫 준비와 같은 입력의 두 번째 준비를 측정해 버전별 네 관측의 중앙값을 구했습니다.
표의 단위는 초입니다. 컨텍스트는 `discovering-components` 시작부터 `preparing-runtime`까지,
번들 구간은 `bundling-modules`부터 워커 응답까지입니다.

| 대상                    | 컨텍스트 기존→수정 | 번들 기존→수정 | 전체 기존→수정 |
| ----------------------- | -----------------: | -------------: | -------------: |
| payroll 과거 임원 패널  |          2.20→1.77 |      9.16→8.81 |    13.77→12.37 |
| VCM 포트폴리오사 페이지 |          1.04→0.96 |      7.86→6.75 |      9.64→9.37 |

payroll 의존성 2,463개·출력 11,292,860바이트, VCM 의존성 2,785개·출력 9,650,922바이트와
각 의존성 순서·CSS 해시·컨텍스트 coverage·진단은 수정 전후 같았습니다. 실행마다 보안 키와
청크 이름이 달라 전체 JavaScript 해시가 같은 것은 아닙니다. 호스트 부하로 일부 개별 실행은
늘었으므로 모든 파일이나 모든 실행에서 같은 비율의 단축을 보장하지 않습니다.

## 검증 범위

초기 회귀 실행에서 파일 동일성 2개와 반복 분석 3개 실패를 확인했고 수정 후 관련 검사가
통과했습니다. 인수/출처 상한·shadow·새 콜백, 편집·복원·byte/entry 제한과 동시 읽기를 포함한
11개 파일·114개 회귀 검사가 통과했습니다. 두 동시 읽기 fixture에는 새 metadata 필드를
추가했습니다. 불완전한 기존 fixture로 발생한 중간 실패는 최종 검사와 구분합니다.

별도 read-only 검토에서 이번 세 production 파일의 캐시 소유권·한도·콜백·소스 무효화를
검토했고 추가 수정 사항은 없었습니다. 검토자가 별도 테스트를 실행한 것은 아닙니다.

현재 전용 루프백 `127.1.0.1`이 인터페이스에 없어 일반 TCP 헤드리스 검증에는 기존 제한이
있습니다. 시스템 주소·정책을 바꾸지 않고 동일 HTML·아티팩트 처리기를 CDP 파이프로 전달하는
진단 전용 메모리 전송을 사용했습니다. 외부 요청은 차단했고 원본 코드는 격리 Chromium에서만
실행했습니다. 이 전송은 제품 변경이나 일반 TCP 전송 검증의 대체 성공 판정이 아닙니다.

수정본의 payroll·VCM 페이지에서 `page-authentic`, 대상 출력과 마운트 1개, 활성 차단 0개,
예외 0개를 확인했습니다. 데스크톱 스크린샷도 확인했습니다. VCM 첫 Chrome 실행은 페이지 진입
전 시작 오류로 종료됐고, 단독 재실행은 통과했습니다. 시작 실패도 검증 기록에 보관합니다.

수정 전후 두 페이지의 DOM 텍스트·선택 라우트·실행 후보·대상 표면도 같았습니다. 그림 파일의
바이트 동일성을 주장하지 않으며 실제 화면을 각각 확인했습니다.

## 전체 검사와 로컬 적용

`npm run check`는 유지 파일 1,870개의 줄 수, strict typecheck, ESLint와 Prettier를 통과한 뒤
전체 테스트에서 종료 코드 1로 끝났습니다. 751개 파일 중 745개, 5,905개 항목 중 5,893개가
통과했습니다. 나머지 6개 파일·12개 실패는 기존 전용 루프백 `EADDRNOTAVAIL`와 그에 따른
실행 전 중단이며 0.1.1710과 실패 이름이 정확히 일치했습니다. 새 테스트 실패는 없었습니다.
일반 TCP 검사나 전체 `check`가 통과했다고 표현하지 않습니다.

별도 production prepublish 빌드와 darwin-arm64 VSIX 검증은 통과했습니다. ARM64 esbuild,
React 18·19, TypeScript 라이브러리와 런타임 170개 파일이 포함되고 로컬 지침·설정·임시 자료는
제외됐습니다. 정확한 검증 패키지를 0.1.1711로 설치한 뒤 전체 payload 2,465개 파일이 설치
메타데이터를 제외하고 패키지와 일치했습니다.

설치된 워커로 과거 임원 패널을 다시 준비하고 격리 Chromium에서 `ready`, 대상 출력과 마운트
1개, 활성 차단 0개, 예외 0개를 확인했습니다. 이 설치본 첫 준비는 16.06초였으며 비교 통계에는
추가하지 않은 한 번의 관측입니다. 브라우저·프로필은 종료·삭제됐고 원본 프로젝트 쓰기 시도는
0건입니다. 설치 전후 모델·최신 학습 입력·설정·사용자 작업 문서 해시는 같았습니다. 기존
0.1.1710의 소스·검사·문서도 해시로 보존을 확인했습니다.

검증 기록은 압축하고 비교용 워커·의존성 복사본·구버전 VSIX는 보호 검사를 거쳐 정리합니다.
최신 VSIX와 설치본·증거는 유지합니다. 사용 중인 VS Code 창을 재로드하지 않았으므로 적용에는
`Developer: Reload Window`가 필요합니다. 시스템 설정 변경·자동 실행·별도 상주 서비스는
추가하지 않았습니다.
