# Context 배열과 사용 페이지 탐색 — 0.1.1680

공유 표의 일반 페이지 사용 위치가 빠지고 모달을 통한 수정 화면만 선택되면서, 상위 페이지의 500 오류와 본문 밖에 분리된 표가 함께 표시됐다. 같은 점수를 받은 원본 배치 후보가 뒤에 있어도 발견 순서 때문에 분리 표시가 먼저 선택됐다.

## 변경과 경계

- 최초 후보와 추가 후보의 대기열을 교대로 읽고, 가까운 소비자부터 디렉터리를 확인한다. 추가 탐색도 한 번에 소진하지 않고 가까운 다른 소비자에 배분한다.
- 추가 탐색에도 기존 일반 후보·페이지 후보의 교차 순서를 사용한다. 실제로 필요한 상위 파일이 일반 후보 75번째였지만 교차 순서에서는 18번째여서 기존 64개 범위 안에 들어왔다.
- 더 높은 기존 의미 점수는 그대로 우선한다. 점수가 같을 때만 원본 안의 배치를 우선하며 모든 후보와 수동 선택은 보존한다. 자동 라우트 분석과 최종 후보 정렬에 같은 규칙을 사용한다.
- 정확한 배열 항목 요구와 타입 리터럴이 있는 경우에만 자동 필드명 문자열을 보완한다. 같은 변경 전 배열과 보완 후 Provider 배열에 약한 참조로 결과를 공유한다. 실제 값·수동 값·getter·비정상 컨테이너는 교체하지 않는다.
- 비어 있지 않은 일반 원시값 배열의 선택 개수는 보존한다. 실제로 없는 숫자 인덱스가 요구된 경우와 빈 배열은 기존 보완 정책을 따른다. 원본 배열이 바뀌면 이전 결과를 재사용하지 않는다.
- 디렉터리 I/O는 최대 4개, 미리 읽은 결과는 최대 64개와 현재 디렉터리로 제한한다. 근처 소스는 8개씩 읽고 기존 순서로 분석한다. 취소·오류 시 시작한 읽기의 종료를 확인한다.
- GraphQL 필드의 별도 길이 읽기와 가져온 Lodash 정렬 함수의 항목 읽기가 함께 확인되면 배열 계약을 전달한다. 정렬 함수는 객체도 받으므로 정렬 호출만으로 배열을 추론하지 않는다. import 별칭·타입 전용 import·가려진 이름·동적 인자와 최대 8개 iteratee 경계를 확인한다.
- 이미 안정적으로 검증한 대상의 실제 탭 패널에서 신뢰된 사용자 클릭·방향키가 확인되면, 다른 탭을 보고 있는 동안 자동 탐색과 학습이 페이지를 다시 마운트하지 않는다. ARIA 연결 또는 탭 목록 바로 뒤의 유일한 표시 패널과 실제 대상 DOM을 확인하며, 다른 탭·합성 입력·오류를 성공으로 인정하지 않는다. 탭·패널 64개·boundary 16개·각 DOM 64개로 확인을 제한한다. 복귀 시 160ms 간격으로 최대 4회 관측하며 실제 출력 확인·DOM 교체 시 관측을 해제한다. 리스너는 기존 페이지 관찰 수명 안에서 설치·제거하고 별도 상주 작업은 만들지 않는다.
- 파일 목록 16,384개, 최초 후보 검사 96/2,048개, 근처·후속 검사 640개, 디렉터리 48개와 추가 탐색 6회·각 64개 한도는 유지한다. 기존 소스·바이트·워커·네이티브 메모리 한도와 사용자 프로젝트 읽기 경계도 바꾸지 않는다.

## 실제 입력 6개 순차 비교

설치된 0.1.1679와 최종 production 후보 SDK를 동일한 읽기 전용 입력에서 순차 실행했다. 사례별 실행 순서를 번갈아 배치했으며 다른 컴파일·검사와 겹치지 않았다. 소스 고정 입력은 29,613개다. 아래 시간은 초 단위이며 최초 컨텍스트·번들링과 제품이 요청한 복구를 포함한 누적 컴파일 시간을 구분한다. 브라우저 시작·UI 조작과 전체 사용자 첫 표시 시간은 이 합계에 포함하지 않는다.

정상 준비는 5/6 → 6/6이다. 모든 최종 후보는 후속 host 컴파일 0회로 준비됐다. 최초 컴파일 합계는 83.40 → 84.86초(1.76%), 복구를 포함한 누적 합계는 95.59 → 84.86초(-11.22%)였다.
누적 컨텍스트는 15.64 → 14.30초, 누적 번들링은 63.47 → 54.81초였다. 최초 컨텍스트 합계는 8.19%, 최초 번들링은 -0.73% 변해 모든 최초 단계의 속도 향상을 주장하지 않는다.
Node CPU는 137.99 → 125.02초, 네이티브 CPU는 27.79 → 23.03초였다. 관측한 Node+esbuild RSS 최대는 2964.64 → 2308.20MiB(-22.14%)다. 기존 정상 사례별 변화는 약 -2.19%~2.92%였다. 1초 표본은 순간 peak를 놓칠 수 있고 Chromium 메모리는 포함하지 않는다.
사례당 한 쌍의 관측치이므로 p95나 일관된 전체 속도 향상을 입증하지 않는다. 이보다 앞선 환경 지연에서 이전 버전과 후보 모두 발견 단계 45초 제한에 걸렸던 기록과 브라우저 시작 실패도 별도 보존했다. 타임아웃이나 시스템·보안·VPN 정책을 늘리거나 우회하지 않았다.

## 스타일과 동작 검증

기존 정상 5개 사례의 첫 CSS 바이트는 동일했다. Tax는 실제 MeetingPage로 연결되면서 해당 페이지의 CSS를 포함하므로 이전의 잘못된 수정 페이지와 CSS hash가 다르다. 원본 CSS를 덮어쓰거나 가려 결과를 맞추지 않는다.
390×844, 768×1024, 1440×900의 렌더링과 실제 메뉴·Escape, 라디오 이동, 텍스트·숫자·확인 입력, Tab을 검사했다. Tax·HeavyTax는 동일한 미수정 번들에서 실제 마우스 탭 클릭·ArrowLeft 복원·원래 대상 출력 복구도 통과했다. HeavyTax 배경 탭 검사는 공개 props 제어로 대상 모달만 잠시 숨긴 뒤 원복했으며 Tax에는 override가 없다. 저장·삭제·수정 제출은 하지 않는다.
원본 법무 페이지의 작은 화면 가로 넘침은 별도 한계로 남아 있다. 수동으로 안건 수정 문맥을 선택할 때 타입 허용값과 실제 안건 그룹이 일치하지 않는 데이터 오류도 이 기본 사용 페이지 선택 수정으로 모두 해결됐다고 주장하지 않는다.

## 전체 검사와 설치

`npm run check`는 5,549개 통과·10개 실패였다. 10개 실패 항목은 0.1.1679와 정확히 같으며 사용 불가능한 `127.1.0.1` 테스트 리스너와 그에 따른 초기 실행·정리 검증 실패다. 줄 수·strict 타입·ESLint·Prettier는 통과했고 새 실패는 없다. 이후 별도의 production prepublish 빌드와 VSIX 패키징도 통과했다.
최종 후보 SDK `6e00d7007f3e82a4acd9fd1d9f116757f513a5b58641250ce16a6e56a18e3500`과 패키지·설치 SDK가 일치한다. 0.1.1680 darwin-arm64 VSIX의 런타임 2,461개 파일과 ARM64 네이티브 실행 파일, 제외 파일을 검증한 뒤 같은 VSIX로 로컬 재설치를 완료했다. 기존 설정·학습 기록 9개 파일의 내용과 권한은 보존됐다.
6개 사례의 18개 화면과 두 탭 화면의 전환·복귀 4장을 직접 확인했다. 실제 페이지 검증은 CDP pipe와 내부 artifact 응답으로 TCP 리스너 없이 수행했다. 원본·읽기 전용 고정 사본 29,613개 파일의 내용과 권한도 다시 확인했다.
종료된 검증 브라우저 프로필 53개를 정리하고 사용하지 않는 SDK 20개의 정확한 압축 사본을 남겼다. 매 삭제 전에 모델 보존 정책을 확인했으며 정리한 논리적 파일 크기는 총 874,319,715바이트(약 834MiB)다. 사용자 데이터·설정·학습 기록은 삭제하지 않았다.
VS Code 창 재로드는 별도로 수행하지 않았다. 설치한 버전을 적용하려면 `Developer: Reload Window`를 실행하면 된다. Marketplace 게시나 git commit·tag·push는 수행하지 않았다.
