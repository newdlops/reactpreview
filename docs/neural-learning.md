# 로컬 신경망의 문제별 학습

Page Inspector의 신경망은 결정적 resolver가 허용한 후보만 평가합니다. 예외, 조건, 데이터
컬렉션, 로컬 UI 상태 전환, 페이지 선택, 페이지 실행, 빈 출력, 렌더 상태, 미렌더링과 일반 문제를
독립된 출력 헤드로 학습합니다. 처음 사용하는 헤드는 중립 점수 `0.5`로 시작하며, 검증된 렌더 결과와
rollback만 온라인 학습 근거가 됩니다. 별도의 [사전학습 복구 모델](neural-pretraining-v2.md)은
저장소 소유 실행 사례로 학습한 시도 순서의 사전값이며, 사용자 프로젝트의 검증 결과로 취급하지 않습니다.

가중치는 같은 유형의 문제 사이에서 재사용하지만 후보의 연속 실패와 성공 기록은 문제 종류 및 제한된
특징 벡터 전체로 만든 문맥 해시별로 구분합니다. 동일한 복구 전략이 다른 데이터 구조에서 실패했다고
현재 문제에서도 실패한 것으로 취급하지 않습니다. 기존 버전 3·4 가중치는 유지하며, 문맥을 알 수 없는
이전 후보 기록은 새 문맥의 실패 횟수로 사용하지 않습니다. 이전에 일반 헤드로 처리하던 페이지 실행과
로컬 UI 전환은 새 전용 헤드에서 중립 상태로 시작합니다.

익명 후보 기록은 프로필 전체에서 최대 192개입니다. 현재 10개 유형마다 최신 19개까지 우선 보존하고,
남는 공간은 전체 최신 기록으로 채워 특정 문제의 반복 학습이 다른 유형의 기억을 모두 밀어내지 않게
합니다. 브라우저 저장·패널 병합·확장 호스트 병합에 같은 보존 규칙을 적용합니다. 저장되는 값은 제한된
가중치, 익명 해시와 검증 결과 카운터이며 프로젝트 소스, 실제 데이터와 특징 벡터는 저장하지 않습니다.

## 특징 정보와 초기 모델 연결

온라인 적응 모델은 입력 64칸과 고정 비선형 투영 16칸을 사용하며, 학습되는 부분은 문제 유형별 출력 가중치 16개와
bias 1개입니다. 10개 헤드를 모두 사용해도 학습 파라미터는 최대 170개입니다. 모델 크기와 학습률은
변경하지 않고, 제한된 입력에 필요한 정보가 남도록 특징 추출을 보강합니다. 버전 0.1.1516의
사전학습 v2 모델은 별도의 `144 → 256 → 64 → 1` MLP이며 53,633개 파라미터를 사용합니다.
기존 프로필의 170개 온라인 파라미터·192개 익명 결과 기록은 호환 상태로 유지합니다.

사전학습은 지원되는 6개 유형의 후보가 모두 학습 범위 안이고 최고 점수 0.8·격차 0.2 이상이거나,
상위 두 후보가 모두 0.9 이상이고 제한된 비용 차감 후 격차가 0.02 이상일 때 순서에 관여합니다.
같은 문맥의 성공 또는 불확실한 시도 기록이 있으면 사전학습을 사용하지 않습니다. 실패만 있으면
실패·제외 후보를 건드리지 않고 미시도 후보가 둘 이상 남았을 때만 다시 비교합니다.
실패 이력과 타입·비용 특징은 사전 모델에만 전달하므로 기존 온라인 문맥 해시는 바뀌지 않습니다.
새 문맥에서는 기존 헤드의 일반화 점수를 근거량에 따라 최대 75%까지
혼합합니다. 사전 점수는 별도 `priorScore`·`priorVersion` 진단이며 성공 횟수·학습 횟수·추천 근거를
증가시키지 않습니다. 수동 선택·정지·허용 후보·반복 예산·rollback·실제 연속 출력 검증은 그대로입니다.

후보 ID와 전략 토큰은 긴 문맥보다 먼저 입력 예산을 배정합니다. `deterministicRank`는 결정적
동점 정렬에만 쓰고 특징·문맥 해시에서 제외해, 순서 변경으로 같은 후보의 실패 기억이 끊기지 않게
합니다. 숫자는 절댓값 1 이하의 기존 `tanh` 표현을 유지하고 그보다 큰 값에는 유계 로그 꼬리를
사용해 8·24·100 같은 개수가 모두 같은 값으로 포화되지 않게 합니다.

기존 가중치와 저장 기록을 초기화하지 않습니다. 동일한 특징 벡터의 기록은 계속 재사용하지만,
특징 표현이 달라진 문맥은 새 기록으로 구분합니다. 원본 특징을 저장하지 않으므로 예전 기록을 새
표현으로 역변환하거나 과거의 잘못된 성공 라벨을 소급 수정하지는 않습니다.

처음 열린 화면은 호스트가 mount에 지정한 revision으로 모델 동기화를 요청합니다. Hot reload는
준비 중인 새 revision을 우선하며, 호스트와 브라우저 모두 다른 revision의 모델 메시지를 계속
거부합니다. 따라서 콜드 시작에서도 프로필에 저장된 가중치를 불러올 수 있습니다.

## 반복 평가와 렌더링 비용

0.1.1519부터 자동 페이지 선택의 빌드 실패와 후보 사용 불가 응답은 렌더 결과와 분리한다.
같은 표시 리비전에서는 해당 후보를 다시 자동 선택하지 않고 다음 허용 후보로 진행하며, 준비 실패
3회 또는 후보 소진 시 자동 준비를 멈춘다. 이 기록은 모델의 실패/성공 횟수나 학습 가중치에 들어가지
않는다. 새 리비전에서는 다시 시도할 수 있고 수동 선택은 항상 허용한다. 마지막 정상 프리뷰와 기존
학습 기록을 유지하며, 호스트가 번들을 적용했다는 사실만으로 성공 판정을 만들지 않는다.
취소·busy·시간 초과·발행 실패는 자동 순환 재시도의 근거로 쓰지 않는다. 후보 ID와 요청 ID를 함께
확인하고, 수동 선택·일시정지·대상/리비전 변경 후에는 예약한 자동 재시도를 폐기한다.

0.1.1521부터 동일 페이지 안의 실행 방식 재빌드도 이 호스트 트랜잭션에 연결한다. 접수 응답은
5초, 접수 후 처리는 최초 응답 기준 150초로 제한하며 진행 메시지가 기한을 갱신하지 않는다.
결정적인 빌드 실패·사용 불가만 미시도 전체 페이지 실행으로 이어지고 같은 표시 리비전의 준비
실패 3회에서 멈춘다. 준비 중단은 렌더 실패 학습이나 모든 페이지 실패 판정과 구분하며, 해당
상태에서 무관한 조건 탐색을 하지 않는다. 새 리비전은 남은 미시도 실행을 허용하지만 기존 실행
시도 한도를 다시 채우지는 않는다. 대기 중 반복 호출은 실제 React 조상을 다시 스캔하지 않는다.
호스트 완료와 요청한 실행의 실제 descriptor 반영을 모두 확인한 뒤 수동 선택을 인계하며,
그 자체로 성공을 학습하지 않고 기존 페이지 문맥·출력 검증을 유지한다. 준비 중단 원인은
`page-execution-preparation-stopped` 로그로 남기고 기존 모델·설정·학습 기록은 유지한다.

import map이 바뀌면 웹뷰 문서 전체가 교체되어 브라우저의 시도 이력이 사라질 수 있다.
따라서 확장 호스트도 페이지·실행 후보 쌍을 기록하고, 같은 입력에서 자동 실행 재빌드를
최대 12회까지만 허용한다. 이미 요청한 후보는 다시 빌드하지 않으며 실패한 준비·핫 리로드·
문서 교체·공개 페이지 후보 변경으로 기록을 지우거나 오래된 시도를 퇴출하지 않는다.
호스트의 중복/한도 거부는 기존 `already-active` 준비 종료로 전달되고, 미해결 페이지 상태와
학습 모델을 유지한다. 수동 페이지 선택은 막지 않는다. 소스·설정 변경이나 명시적 새로고침으로
일반 빌드를 준비할 때, 또는 다른 경로 선택을 확정했을 때만 새 실행 탐색 예산을 시작한다.

동기 후보 선택 한 묶음은 저장된 모델을 한 번만 검증하고, 허용된 후보 각각을 한 번만 추론합니다.
정렬 비교에서는 이미 구한 점수를 재사용합니다. 다음 묶음은 다시 모델을 검증하므로 학습·복원·손상된
저장 상태가 이전 캐시에 가려지지 않습니다. 별도로 보관한 결정의 비교와 요약도 최신 모델로 재평가하며,
후보 한도·중립 점수·실패 기억·분기 유지·동점 정렬 규칙은 그대로 유지합니다.

학습 상태의 변경은 툴바의 학습·요청·선택 컨트롤만 구독합니다. 같은 작업 안의 변경은 한 번에 알리고,
대상 페이지와 Inspector 트리의 전체 구독에는 전달하지 않습니다. 구독은 unmount 시 해제하고,
렌더와 effect 사이의 변경도 반영합니다. 별도 Inspector 탭에는 컨트롤 commit 후 기존 snapshot을
예약하므로 진행 표시가 멈추지 않습니다. 실제 값·대상·분기 변경의 기존 전체 알림은 유지합니다.

2026-09-06 로컬 후보 평가 벤치마크는 10개 헤드·192개 익명 기록·결정당 12개 후보로 측정했습니다.
20회 예열 후 100회 선택을 5번 실행한 중앙값은 4,986.96ms → 658.39ms였고, 프로세스 CPU 시간은
4,993.78ms → 624.63ms였습니다. 최종 결정의 SHA-256이 같았으며 모델 전체 검증은 선택당 124회에서
1회로 줄었습니다. 이는 합성 후보 평가 구간의 수치이며 전체 페이지 렌더 시간이나 메모리 감소율이
아닙니다. `node scripts/benchmark-neural-selection.mjs`로 현재 구현을 다시 측정할 수 있습니다.

### 오류 블로커와 전체 선택 경로의 평가

hook·backend 요구는 현재 오류의 필드와 root-to-target 경로로 먼저 선별한 뒤 신경망을 실행합니다.
같은 선별 과정에서는 오류 정보를 한 번만 읽고, 허용된 후보만 한 번씩 추론합니다. 보관된 결정도 같은
검증된 모델로 새 점수·실패 이력을 계산하며 원본 결정은 변경하지 않습니다. 유효하지 않은 결정은 현재
후보 근거로 대체합니다. 모델은 동기 평가 한 묶음에서만 공유하고 다음 평가에서는 다시 검증합니다.

실패로 제외된 후보는 같은 허용 집합에 새 후보가 있을 때 뒤로 보냅니다. 오류와 관련된 필드가 많거나
shape mismatch 표시가 있다는 이유로 제외를 무시하지 않습니다. 새 후보를 찾으려고 오류·경로와 무관한
집합으로 범위를 넓히지는 않습니다. 선택 경로도 같은 종료 상태 안에서는 최근 실패 이력을 일반화된
신경망 점수보다 우선합니다. 실제 출력 검증·추천 근거 기준과 사람이 직접 값을 적용하는 기능은 유지합니다.

관찰된 선택 경로는 탐색 한 번마다 출발 상태·선택 조합별로 색인합니다. 매 조합마다 전체 간선을 다시
훑지 않지만 색인은 다음 탐색에 보관하지 않으므로 새 성공·순환·삭제 근거가 바로 반영됩니다. 120개
간선·64개 조합 회귀 사례에서 출발 상태 확인은 7,680회에서 120회로 줄었습니다.

`node scripts/benchmark-neural-blocker-ranking.mjs`는 10개 헤드·192개 기록으로 2회 예열 후,
10회 평가를 5번 측정합니다. 2026-09-06 측정 결과는 다음과 같으며 두 사례의 결과 해시는 전후 같습니다.

| 합성 평가 구간                    | 변경 전 중앙값 | 변경 후 중앙값 | 평가당 모델 검증 / 추론 횟수 |
| --------------------------------- | -------------: | -------------: | ---------------------------- |
| 123개 요구에서 경로 내부 3개 선별 |       532.22ms |        10.96ms | 127 / 127 → 1 / 3            |
| 유한 선택 경로 64개 정렬          |     2,090.93ms |       193.29ms | 530 / 530 → 1 / 64           |

이 수치는 각 구간을 10번 실행한 시간이며 실제 프로젝트 전체의 렌더 지연·메모리 사용량이나 해결률을
나타내지 않습니다. 실패 후보의 우선순위 변경은 별도의 회귀 사례로 검증합니다.

### 런타임 목표 경로 탐색

JSX 조건을 따라가는 런타임 탐색도 목표 경로·사용자 값·현재 분기·실행 가능 여부를 먼저 확인합니다.
이미 만족됐거나 관련 없는 조건에는 모델을 실행하지 않으며, 동기 조회마다 모델을 한 번 검증하고
허용된 조건을 한 번씩 추론합니다. 전체 후보 정렬 대신 다음 조건 하나를 선형 선택합니다. exact target,
일반 경로, authored-state 대기 검사는 같은 평가의 소유자 근거를 공유하되 다음 commit까지 캐시하지 않습니다.

각 조건에는 소스 위치·표현식·분기 방향의 익명 ID를 부여하고 authored route·목표 소스로 학습 문맥을
구분합니다. 발견 순서는 실패 기억의 신원에서 제외하고 중립 점수의 안정된 결정 순서로만 사용합니다.
새 후보를 찾으려고 경로 밖으로 범위를 넓히지 않으며, 사용자 override·모호한 overlay 소유권·실제 출력
검증·기존 탐색 예산과 rollback은 유지합니다. 중첩 JSX 라벨의 태그 경계를 공백으로 보존하여 이름이
붙어 사라지지 않게 하고, 한 라벨의 점수·컴포넌트·정확한 목표 일치를 함께 조회합니다. 신경망 상태의
속성 경로는 own data descriptor만 읽으며 getter나 상속 속성을 실행하지 않습니다.

`node scripts/benchmark-runtime-target-path.mjs 20`은 조건 126개 중 경로 내부 6개, 10개 헤드,
192개 익명 기록으로 5회 예열 후 20번 조회를 5회 측정합니다. 2026-09-07 로컬 중앙값은
1,686.92ms → 81.84ms, CPU 시간은 1,597.36ms → 79.14ms였습니다. 조회당 모델 검증은
136 → 1회, 추론은 136 → 6회, 소유자 중복 스캔은 2 → 1회였으며 모든 후보에 같은 점수를 주는 모델의
선택 ID·방향 결과 해시는 전후 일치했습니다. 이는 합성 경로 조회 구간의 측정이며 전체 페이지 렌더
시간이나 실제 프로젝트 해결률의 측정은 아닙니다. 실패 기억·토큰 경계·수동 제어는 별도 회귀로 검증합니다.

### 자동 복구 가능 여부와 실제 실행 선택

진행 표시에서 자동 복구가 남았는지 확인할 때는 경로 점수를 추론하지 않습니다. 현재 선택지는 한 번만
읽고 같은 의미 상태에서 이미 수집한 유한 조합을 재열거하지 않습니다. 대기 중인 경로의 실제 상태
관찰은 계속 수행하므로 이 최적화가 관찰 결과에 따른 학습을 막지는 않습니다.

실제로 실행할 때는 미시도·비기본값 조합만 현재 모델로 평가합니다. 한 실행 선택에서 모델을 한 번
검증하고 각 후보를 한 번 추론하며, 최근 연속 실패를 일반화된 점수보다 먼저 반영합니다. 경로의 의미
정보는 보존하되 선택 점수를 작업 간 캐시하지 않으며, 이전 hot reload가 보관한 결정도 최신 모델로
재검증합니다. 이미 반환한 결정·수동 값·학습 기록은 덮어쓰지 않습니다. 새 상태가 추가되어도 보관하는
자동 조합 수는 96개를 넘지 않습니다.

`node scripts/benchmark-neural-page-generation.mjs`는 10개 헤드·192개 기록·64개 조합으로
2회 예열 후 각 동작을 10번씩 5회 측정합니다. 2026-09-06 중앙값은 가능 여부 조회
159.80ms → 1.24ms, 실제 실행 선택 157.61ms → 144.79ms였습니다. 조회당 모델 검증·추론·
그래프 열거는 각각 1·64·1회에서 모두 0회가 되었으며, 실제 선택은 기본값 조합을 제외한 63개만
추론합니다. 같은 모델에서 결과 해시는 전후 일치했습니다. 이 수치는 합성 동작 구간의 측정이며 전체
페이지 렌더 시간·메모리 감소율·해결률이 아닙니다.

## 예외 근거와 타입별 자동 복구

속성 읽기·호출 실패뿐 아니라 명시적인 `props.items is not iterable`, Safari의 `evaluating`
속성 경로, Firefox의 `can't access property` 진단을 읽습니다. 래퍼 오류에 유효한 경로가 없으면
`cause`를 최대 8개까지 확인합니다. 가장 가까운 유효한 오류의 경로만 사용하며, 여러 오류의 필드를
합치거나 `AggregateError.errors`를 탐색하지 않습니다. 감싸진 `ReferenceError`도 데이터 누락과
구별해 prop을 생성하지 않습니다.

진단마다 앞부분 4,096자와 최대 32개 경로만 보관하고, 240자를 넘는 경로는 잘라 적용하지 않고
버립니다. 오류의 자체 데이터 속성을 읽어 getter와 프로젝트의 문자열 변환을 호출하지 않으며,
순환 참조·접근 불가능한 proxy에서는 진단을 중단합니다. 원래 오류의 표시 기능과는 별개입니다.

자동 prop 복구는 선택 export의 소유권, 같은 소스, 유일한 compiler 경로와 알려진 타입을 모두
확인합니다. `props.`/`this.props.`를 최종 타입 확인에서도 정규화하고, `length`는 배열·문자열로
확인된 수신자만 복구합니다. 타입에 맞는 배열·문자열·콜백 등 기존 생성기를 사용하며 사용자 입력을
덮어쓰거나 bare 로컬 변수·모호한 오류를 외부 prop으로 추측하지 않습니다.

## 렌더 결과를 학습하는 기준

0.1.1520부터 생성 라우터의 존재를 실제 상위 페이지 실행과 구분합니다. 상위 route owner가 없는
경로에서는 컴파일러가 확인한 헤더·푸터 등 주변 영역을 그대로 조립하며, 앱 진입점이나 무관한
route registry를 추가 실행하지 않습니다. 실제 owner가 그리는 영역은 중복 조립하지 않습니다.

페이지 성공에는 선택된 실행 페이지와 유지해야 하는 owner·layout이 대상의 실제 React 조상으로
관찰되어야 합니다. 다른 소스의 안쪽 컴포넌트 이름이나 정적 표시 경로로 이를 대신하지 않습니다.
문맥이 빠지면 출력은 복구 재료로 유지하되 성공 확정·학습을 보류하고 기존 유한 후보로 복구를
계속합니다. 수동 컴포넌트 보기와 일시정지는 예외로 유지하며, 조상 검증은 모든 형제 영역의
내용·조건부 표시까지 보장하는 시각적 검증은 아닙니다. 사전학습 가중치는 변경하지 않습니다.

대상이 있는 복구 시도는 캐시된 `reached` 상태나 중간 blocker의 소멸만으로 성공 처리하지 않습니다.
대상의 mount·페이지 commit 상태가 출력과 모순되지 않아야 하며, 기존 target-owned host output
검증기로 실제 출력을 다시 확인합니다. 출력이 있는 긍정적 학습은 160ms 간격으로 연속 3회 확인한
후에만 반영하고, 중간에 출력이 사라지면 관찰 횟수를 다시 셉니다. 기존 960ms 관찰 한도까지 충분한
안정성 근거를 얻지 못한 일시적 출력은 성공으로 학습하지 않습니다.

출력 일부가 보이더라도 현재 목표를 막는 조건·필수 데이터·fallback·오류가 남아 있으면 완성된
렌더로 보지 않습니다. 각 관찰에서 활성 blocker를 다시 확인해 성공 저장과 성공 학습을 보류하고,
해결된 뒤에 연속 관찰을 다시 시작합니다. 일반 조건 분기 `◇`는 오류가 아니며, 필수 선택 `?`가
남은 화면은 `PAGE INCOMPLETE`로 표시합니다. 모델 갱신 횟수와 페이지 해결 여부는 구분합니다.

생성 데이터가 predicate를 통과하더라도 대상이 표시되지 않으면 렌더 성공이 아닙니다. 수렴 중에는
출력을 기다리고, 끝내 출력이 없으면 낮은 신뢰도의 부분 진전으로만 기록합니다. 이 결과로 기존 허용
후보 중 다른 전략을 다음에 시도할 수 있으며, 새로운 후보나 강제 실행 권한을 만들지는 않습니다.

hook fallback의 데이터 통과 카운터는 해당 렌더 시도에만 연결하며 별도 타이머로 학습하지 않습니다.
대상 없는 카운터나 끝내 호출되지 않은 predicate는 학습을 보류합니다. 컴파일러가 허용한 identity
참조도 후보일 뿐 정답이 아닙니다. 코드가 임의의 0·1 라벨을 반복 학습해 특정 후보를 강제로 승격하지
않으며, 실제 실패가 확인되면 같은 허용 집합의 다른 값으로 전환할 수 있습니다. 함수의 표시 문자열이
같더라도 후보 전략이 달라지면 새 렌더 시도로 기록합니다.

대기 중 페이지·export·대상 상태 객체·소스 revision·수동 제어 revision·실행 시도가 바뀌면 이전
관찰을 학습에서 제외합니다. 같은 시도의 rollback과 유예 기간 내 fatal error는 실패로 반영하고
예약된 성공 관찰을 취소합니다. 기존 오류 귀속 유예 기간과 자동 복구 실행 범위는 늘리지 않습니다.
이 신원은 관찰 시작이 아니라 시도 생성 시점부터 보존합니다. 자동 fallback의 오류는 값을 임의로
되돌리지 않더라도 해당 신경망의 성공 학습을 취소합니다. 신경망 선택·학습·보정 및 페이지 실행
검증 이벤트는 브라우저와 호스트 양쪽의 명시적 허용 목록으로 전달하고, 잘못된 메시지는 계속 거부합니다.

## 시도 종료와 다음 탐색

렌더 시도가 끝나기 전에는 재개 요청이 와도 대상 탐색을 잠금 해제하지 않습니다. 정상 종료된 시도는
추가 타이머 없이 한 번만 재개하므로 정지된 webview 타이머 때문에 계속 대기하는 일을 피합니다.
다른 결정에 합쳐져 실제 결과를 관찰하지 못한 `superseded` 시도는 되돌리거나 학습하지 않습니다.

값을 바꾸지 못한 복구와 변경 없이 던진 예외에는 표시용 600ms 대기를 붙이지 않습니다. 다음 허용
시도는 프레임 큐로 넘기며 기존 유형별·전체 작업 예산을 유지합니다. 값이 바뀌었거나 부분 변경의
렌더 trace·fallback 재시도·대상 시도가 남아 있으면 대기와 잠금을 유지합니다. 계속 시도 중인
상태를 중단으로 표시하지 않으며 출력 안정성 검증, 소스 변경 취소와 사람의 일시정지는 그대로입니다.

검증 후 진전이 없어 되돌린 JSX 분기는 다음 후보가 시도를 인계받기 전에 실패 라벨을 반영하고,
대상 상태를 `probing`으로 전환합니다. 그 결과는 trace와 health 로그 모두 `rolled-back`으로
기록하며, 중복 관찰이 다시 성공 점수를 주지 못하게 합니다. 복구 rollback 로그의 hook·prop·request
개수도 호스트까지 전달해 무엇을 되돌렸는지 확인할 수 있습니다.

fallback의 메타데이터·값·공유·추천·해결·effect·override와 trace의 기록·선택·오류 처리는 별도
소스 생성 모듈로 분리했습니다. 이들은 계속 같은 브라우저 모듈의 lexical scope에 조합되므로
프로젝트 코드에 새 API나 호스트 권한을 노출하지 않습니다.

## 추천과 사람의 판단

신경망은 허용된 복구 후보의 순서를 평가하는 보조 모델입니다. 새로운 해결책을 만들거나 페이지의
버튼이 현재 오류를 해결한다고 추측하지 않습니다. 페이지 선택지는 컴파일러에 등록된 핸들러가 현재
조건과 같은 소스·컴포넌트·상태 변수를 변경하며, 해당 핸들러가 실제 DOM에 연결된 경우에만 표시합니다.
관계를 입증하지 못하거나 제어가 너무 많으면 직접 페이지를 조작하거나 상세 편집기를 열도록 안내합니다.

### 페이지 문맥 기반 다음 단계

`Page-aware next steps`는 전체 값의 곱집합을 먼저 보여주지 않습니다. 실제 authored route, 페이지 루트,
선택 컴포넌트와 소스, 현재 조건·오류의 필드 요구를 연결해 한 번에 한 결정만 바꾸는 후보를 만들고
기존 신경망으로 순서를 평가합니다. 목표 컴포넌트가 조건의 falsy 분기에 있으면 false 방향을 사용하고,
실패가 특정 prop을 가리키면 그 필드만 제안합니다. 소스 경로가 확인된 필수 데이터는 Smart 최소값,
로컬 상태는 기존의 정확한 handler/DOM 증명을 통과한 제어만 사용합니다. 관련 없는 테마 값이나
일반 버튼을 페이지 목적의 근거로 삼지 않습니다.

앞의 3개 다음 단계에는 변경 이유와 출력 검증 여부를 표시하고 나머지 문맥 후보와 전체 수동 편집은
접힌 영역에 보존합니다. 소스가 관련 변경임을 보여주는 것과 신경망이 추천할 만큼 성공을 학습한 것은
구분합니다. 근거가 부족한 경우에는 추천을 보류하며, 사용자 클릭 없이 새 동작을 실행하지 않습니다.
적용 직전 route·현재 값·후보 신원을 다시 확인하고, 단일 prop 제안은 나머지 필드를 변경하지 않습니다.
추론과 실제 선택 결과의 학습에는 같은 문맥 특징을 사용하며, 새 실패가 있으면 과거 검증 표시를 철회합니다.

문맥은 제한된 소스 메타데이터를 사용하고 URL query/hash와 전체 데이터 payload는 읽지 않습니다.
웹뷰의 생성 주소 대신 authored route를 특징으로 사용하며 페이지별 실패 기억과 탐색 상태를 분리합니다.
이는 대규모 언어 모델의 업무 의도 이해나 자유로운 해결책 생성이 아닙니다. 자동 복구 내부의 유한 조합
탐색·원상복구·출력 검증 정책은 유지하고, 사람이 보는 다음 단계 생성과 공통 순위 모델의 입력을 개선합니다.

### 추천 근거와 수동 제어

초기 점수 `0.5`는 추천 근거가 아닙니다. 안정된 출력이 검증된 경로 또는 반복된 후보 결과와 충분한
점수 차이가 있는 경로만 추천합니다. 후자의 보수적 표시 기준은 헤드 근거량 3 이상, 같은 문맥에서
후보 시도 2회 이상, 연속 실패 없음, 선택 점수 0.65 이상, 차순위와의 차이 0.05 이상입니다. 이 점수는
보정된 성공 확률이 아닙니다. 근거가 부족하면 추천을 보류하되 사람이 직접 선택하는 기능은 유지합니다.
조합이 96개를 초과하거나 후보·깊이 한도에 걸리면 일부만 잘라 순위를 매기지 않습니다. 구체적인 값은
선택 그룹에 남겨 한 결정씩 범위를 좁힐 수 있게 합니다.

자동 탐색 중에는 **Pause automatic**, 중단 후에는 **Resume automatic**을 사용할 수 있습니다.
중단은 대기 중인 신경망 재시도와 복원 관찰을 무효화하며 이미 적용된 값과 학습 기록을 지우거나
되돌리지 않습니다. 값을 직접 적용해도 자동 작업이 중단됩니다. 선택 그룹은 탐색·복원 중에도 접근할
수 있고, 나머지 결정은 접힌 상세 영역에서 열 수 있습니다. 이미 실행 중인 동기 코드나 호스트 빌드는
소급 취소하지 않으며, 새 소스 revision 또는 다른 대상에는 중단 상태가 적용되지 않습니다.

### 시작 비용과 복구 직전 재검증

미학습 헤드의 점수 조회는 중립값 `0.5`를 반환하며 숨은 층 투영을 하지 않습니다. 검증된 첫 학습은
투영을 정상 실행합니다. 학습된 헤드는 1,024개 고정 가중치를 한 번 지연 생성해 재사용하고, 입력 순서와
산술식을 유지해 기존 점수·SGD·저장 모델을 보존합니다. 페이지 값·후보 점수·학습 상태를 캐시하지 않습니다.
렌더·학습 대기 프레임은 전체 블로커를 재분석하지 않고, 대기가 끝나면 현재 범위와 근거를 다시 읽습니다.

모든 허용 후보가 실패한 경우에는 연속 실패가 적은 방향을 우선하고 동률에서 학습 점수를 비교합니다.
실패 기억은 기존 문제 문맥 안에서만 적용됩니다. 준비와 적용 사이에 페이지·대상·수동 제어·오류의
필수 경로 또는 유한 선택 도메인이 바뀌면 이전 전략을 적용하지 않고 기존 예산 안에서 다시 계획합니다.
이미 예약한 마지막 시도는 보존하며, 수동 값·출력 안정성 검증·rollback·최대 대기/시도 한도는 유지합니다.

### 선택지의 출처와 선택 상태

선택지 열기 버튼에는 `Choose status`처럼 결정할 필드와 `pending / responded` 같은 실제 옵션을
함께 표시합니다. 여러 결정은 최대 3개 결정·결정별 3개 옵션을 요약하고 생략한 수를 명시하며,
전체 수동 옵션은 목록에 남깁니다. 클릭은 목록을 펼치고 포커스만 이동합니다. 원래 페이지 값을
선택·적용하거나 상세 탭으로 이동하지 않습니다. 별도 Inspector도 같은 동작을 사용하며, 이후
일반 갱신에서는 옵션 목록의 스크롤·수동 선택을 보존합니다. 선택지가 없으면 `Inspect blocked step`,
페이지 문맥을 고르는 경우에는 `Compare page paths`로 다른 목적을 명확히 표시합니다.

실제 추천 경로와 그 경로의 현재 옵션에는 `Neural choice` 배지와 테두리·배경 강조를 표시합니다.
색을 보지 않아도 배지와 접근성 이름으로 추천을 알 수 있습니다. 배지는 직접 선택·적용·출력 검증을
뜻하지 않으며, 원래 페이지 옵션도 추천 대상이면 출처와 추천 표시가 함께 나옵니다. 추천이 없으면
`No neural recommendation yet`을 표시하고 모든 수동 옵션은 유지합니다. 현재 경로·선택 그룹·후보의
신원이 일치할 때만 옵션을 강조하며, 오래된 문맥·불완전한 후보 매핑·새 실패·탐색 한도 초과에서는
추천 표시를 보류합니다. 이 표시는 추가 추론·학습·effect·페이지 DOM 변경을 실행하지 않습니다.

`Inspector Choice`의 옵션에는 출처를 별도로 표시합니다. `Original page option`은 동일 소스의
실제 렌더된 페이지 컨트롤을 확인해 옮겨 보여주는 항목입니다. `Code-defined value/branch`는 코드에서
찾은 값·분기를 프리뷰에서 시험하는 Inspector 제어이며, 원래 페이지에 해당 버튼이 있다는 뜻은 아닙니다.
`Inspector recovery/reset`은 프리뷰용 생성·초기화 동작입니다. 지원되는 근거가 없으면 `Source unverified`로
남기고, 조합된 다음 단계는 `Inspector proposal`로 표시해 기존 페이지의 옵션으로 오해하지 않도록 합니다.

출처는 추천 점수·선택·성공 여부로 바뀌지 않습니다. `Current`와 `Selected`를 함께 유지하고 관찰된 실제
선택에는 `On page now` 또는 `In preview now`를 표시합니다. 선택은 적용이 아니며, 기존 Apply/Continue
버튼으로만 반영합니다. 출처 표시는 모델 호출·DOM 탐색·상태 저장을 추가하지 않습니다.

### 표시 실패의 원인과 경로 근거

Inspector는 `Page path`와 `Render logic`을 독립적으로 표시합니다. 소스의 호출 연결은 정적 근거일
뿐, 실제 페이지 문맥에서 목표가 실행됐다는 증거는 아닙니다. 현재 목표를 막는 실행된 조건이 있으면
조건식·현재 ON/OFF·추론된 목표 분기·소스 위치를 보여주고 `Inspect blocking condition`으로 이동합니다.
이동만으로 조건 값이나 페이지를 바꾸지는 않으며, 경로가 바뀌거나 해소된 조건에는 오래된 이동을 적용하지 않습니다.

컴포넌트 수준 fallback만 복원한 경우는 원래 페이지 문맥 미확인으로 표시합니다. 부모의 미호출 콜백,
목표 실행 후 빈 출력, 렌더 오류도 미도달과 구분합니다. 목표가 보이지 않는 사실만으로 경로 오예측을
단정하지 않으며, 조건 근거도 없으면 원인 미확인과 `Inspect path evidence`를 안내합니다.
관찰되지 않은 API 상태 값이나 업무 의미를 추측하지 않고 기존 탐색 예산과 성공 검증은 유지합니다.

## 후보 데이터의 필수 필드

### 현재 페이지 문맥에 귀속되는 학습 결과

Page choice의 성공·실패는 현재 descriptor, 실행 가능한 페이지 후보, 목표 export·소스 경로,
활성 reachability 상태 객체와 entry 리비전이 일치할 때만 반영합니다. 페이지 전환·소스 교체 후
도착한 이전 콜백과 일시정지 중인 작업은 학습·저장·자동 경로 전환을 하지 않습니다.
교체된 상태의 provisional 표시도 남기지 않습니다. 선택 힌트나 컴포넌트 출력만으로 페이지를 증명하지 않습니다.

실제 페이지·layout의 React 조상 이름은 일치하는 신원을 요구합니다. `UsersPageSkeleton`이나
`ArchivedUsersPage`는 `UsersPage`의 증거가 아닙니다. `memo(UsersPage)`,
`withRouter(UsersPage)`처럼 괄호로 구분된 HOC는 최대 8단계까지 해석하고 잘못되거나 과도한
이름은 인정하지 않습니다. 기존 compiler-proven 별칭은 유지하며 관찰된 이름을 한 번 색인합니다.
이름 비교는 의미 추론이나 소스 신원 증명의 대체물이 아니므로 정확한 목표 boundary 검증도 유지합니다.

안정 출력 플래그가 있어도 활성 blocker, 목표 오류, 복구 대기, 분리된 DOM, 불완전한 페이지가
있으면 성공으로 학습하지 않습니다. 복구 중인 오류나 검증기에서 관찰하지 못한 결과는 판단을 보류하고,
기존 안정성 검증기가 확정한 퇴행·종료된 page-blocked만 실패로 반영합니다. 이때 일부 DOM이 남아
있다는 이유로 성공 기록을 유지하지 않습니다. 학습 판정 단계는 아직 결론이 없거나 이미 반영한 결과에서
Fiber를 재탐색하지 않고, 필요한 결과의 페이지 문맥도 한 번만 관찰합니다. 새 모델 학습량이나 일반 해결률 증가를 뜻하지 않으며,
기존 사전학습 가중치와 개인 학습 데이터는 그대로 보존합니다.

### 페이지 주변 영역의 복원 경계

페이지 구성 오류는 학습량 부족과 구분합니다. `route-branch` 분류나 PascalCase 이름만으로는
React 컴포넌트임을 증명하지 못합니다. 권한 enum·설정 값을 JSX로 만들지 않고 실제 JSX·컴포넌트
슬롯 근거를 요구합니다. import로 확인된 React Router의 Route 경계를 발생 위치별로 비교하여
다른 경로의 탭은 대안으로 분류합니다. 동일 컴포넌트의 현재 경로 사용이나 바깥 헤더는 유지합니다.
다른 경로의 모듈도 일반 데이터로 함께 참조된다면 제한된 분석 의존성에는 남기지만 화면에 붙이지 않습니다.

반복 탭의 고유 이름 수가 적어도 실제 트리 노드 수가 분석 한도에 도달하면 누락 가능성을 표시하고
owner 근거로 보완합니다. 분리해서 생성하는 sibling 영역은 그 모듈·export의 타입과 사용 근거로
필수 props를 추론합니다. 한 준비 요청 안에서 같은 소스와 추론을 재사용하고 현재 편집 내용을 우선합니다.
기존 props materializer와 fallback 켜기/끄기를 공유하며 명시적 null·실제 값은 덮어쓰지 않습니다.
목표 컴포넌트·이미 부모가 렌더링하는 자식·선택되지 않은 optional 모듈에는 이 경로를 적용하지 않습니다.
주변 영역의 출력만으로 성공을 만들거나 예외를 숨기지 않습니다. 실제 목표 출력·페이지 문맥 검증은 유지됩니다.

### 중첩 후보 필드의 완전성

복구 시도 후 같은 누락 필드 오류가 반복된다면 점수 조정보다 후보 데이터의 완전성을 먼저 확인합니다.
`query.data.items → filteredItems → helper({ item })`처럼 목록의 항목 신원이 유지되는 경로에서는
helper가 읽는 중첩 필드를 원래 hook의 생성 값과 `requiredPaths` 양쪽에 전달합니다. 같은 목록의
여러 callback 요구도 마지막 reader 하나로 덮어쓰지 않고 공유 항목 병합 규칙으로 합칩니다.
일반 hook 분석뿐 아니라 실제 변환에서 우선되는 Context 전용 fallback에도 같은 imported helper
근거를 전달합니다. 개별 분석기의 생성 값이 충분하더라도 최종 변환의 다른 fallback이 선택되면
누락 오류가 남을 수 있으므로 전체 `PreviewSourceTransformer` 결과로도 회귀 검증합니다.
임의 함수 호출, 항목을 바꾸는 `map`, 가변 별칭은 같은 항목이라는 근거가 없으므로 역전파하지 않습니다.
