# 모듈 경로 해석 성능 기록

## 0.1.1668: 모듈 경로 결과 공유

정적 모듈 해석은 consumer마다 TypeScript로 정확한 파일을 선택한 다음 실제 경로를 확인한다.
여러 consumer가 같은 파일을 선택하면 기존 4,096개 positive 해석 답이 보관되는 동안 그
경로 문자열을 공유한다. 마지막 참조가 제거되면 경로 색인도 제거한다. 다음 요청은 새 해석기를
사용하며, 실패·미해결 답이나 소스 AST를 새로 보관하지 않는다. 파일시스템 조회 한도 4,096개,
주 워커 4 GiB, Sass 한 작업 512 MiB·30초와 그래프·출력·준비 완료 한도는 유지한다.

공유되는 것은 TypeScript가 같은 실제 파일을 선택한 뒤의 경로 확인이다. issuer별 설정과
패키지 선택은 계속 독립적으로 수행한다. 보안 경계의 직접 경로 검사는 변경하지 않는다.

## 관측한 반복 작업

기존 production 워커의 보존된 40.9초 CPU 기록에서 정적 모듈 해석 뒤의 경로 확인이 약
4.6초를 차지했다. 별도 계측 워커로 같은 VCM Section 입력을 컴파일한 호출 횟수는 아래와 같다.
계측은 호출을 그대로 전달하며 결과를 바꾸지 않는다. 이 표는 전체 로딩 속도 개선율이 아니다.

| 항목                 |   기존 |   수정 |
| -------------------- | -----: | -----: |
| native realpath 호출 | 23,688 | 15,171 |
| 고유 경로            |  5,029 |  5,029 |
| 기존 실패 호출       |  1,344 |  1,344 |
| 의존성 수            |  2,058 |  2,058 |

호출은 약 35.95% 감소했고 CSS·의존성·진단 결과는 같았다. 초기에 시험한 타깃 전용 캐시와
별도 파일시스템 캐시는 전체 대기를 줄이지 못해 제외했다. TypeScript의 기존 realpath 결과만
재사용하는 후보도 실제 VCM 호출 수를 줄이지 못해 제외했다. 실패한 측정과 코드는 보존했다.

## 기능·속도 검증의 범위

새 회귀 검사는 여러 issuer의 공유, 다음 요청의 링크 교체, 기존 해석 캐시에서 마지막 참조가
제거된 뒤의 재조회, 같은 패키지 이름의 서로 다른 설치, 선언 파일의 runtime sibling 선택을
확인한다. 쿼리별 캐시 슬롯 검사는 다른 실제 파일을 사용해 마지막 참조의 제거도 확인한다.
관련 4개 파일의 30개 검사가 통과했다.

전체 검사 중 별도 Git 스냅샷 검사가 15초 한도를 넘었다. 테스트 저장소는 Git 호출 4회로
한 번만 만들고, 각 검사는 `.git`과 작업 파일을 독립 복사한다. 두 번의 스냅샷 작업을 묶었던
링크 거부·내용 변조 검사를 나누고 모든 검증 항목을 유지한다. 호출을 그대로 전달한 계측에서
Git·tar 33회 중 `git ls-tree` 한 번이 약 7.1초 걸렸으며, 같은 15초 한도에서도 실행별로
통과와 시간 초과가 달랐다. 실제 외부 도구를 쓰는 스냅샷 검사와 공통 저장소 준비에만 30초
한도를 적용한다. 다른 단위 검사와 제품의 준비 완료·메모리 한도, 실제 스냅샷 구현,
사용자 저장소의 Git 설정은 변경하지 않는다.

고정된 fast·corridor 입력 4개의 cold/warm 16회 비교에서 CSS·의존성·페이지 구성 근거는 모두
같았다. 수정본 8회는 모두 대상 출력까지 도달했다. 기존 워커 2회는 셸만 그려진 채
insufficient-evidence로 끝나므로 전체 비교를 통과했다고 표현하지 않는다. 전체 로딩 개선 주장에
필요한 일관된 쌍별 개선 기준도 통과하지 못했다.

이 비교의 IR 수정본에는 cold 65.6초·warm 45.3초 지연도 남아 있다. 이전 문서가 누적되는
영향을 분리하기 위해 컴파일러 비교 단위마다 브라우저를 종료한 별도 AB/BA 검사를 수행했다.
8회 모두 ready와 동일한 CSS·의존성·페이지 근거를 확인했고 cold/warm의 컴파일·전체·Node CPU
중앙값 5% 초과 회귀 금지 기준을 통과했다. 두 쌍뿐이며 실행 간 차이가 커 전체 로딩의 일반적인
개선율은 확정하지 않는다. Node CPU에는 별도 native esbuild 프로세스가 포함되지 않는다.
앞선 지연의 원인을 브라우저나 OS만의 문제로 확정하지 않는다.

## 화면과 갱신

실제 VCM 조합원 페이지의 1440×900·768×1024·390×844 화면을 기존 버전과 직접 비교했다.
글꼴·색·간격·표·lazy CSS의 계산된 스타일이 같고, Tab 포커스·초대창 열기·취소와 같은 번들의
두 차례 새로고침 검사가 통과했다. 초대창과 마지막 새로고침 화면도 직접 확인했다.

기존·수정본 모두 좁은 화면에서 본문이 가려지고, 첫 표시와 캐시된 갱신 뒤의 본문 너비가 다른
현상이 남아 있다. 이 변경은 해당 레이아웃이나 런타임 동작을 수정하지 않는다. 모든 프리뷰의
1분 이상 대기가 해소됐다고 주장하지 않으며, 확인된 중복 파일시스템 작업만 줄인다.

검증 서버는 127.1.0.1, CDP는 pipe를 사용했다. 원본 프로젝트·설정·학습 기록과 시스템 정책을
변경하지 않았고 새 의존성이나 자동 실행·상주 서비스를 추가하지 않았다.

## 0.1.1669: 중복 상대 경로 정규화 제거

컴포넌트 문맥 탐색과 번들 준비에서 사용하는 `path.relative()`는 두 입력을 내부적으로
정규화한다. 같은 입력에 먼저 `path.resolve()`를 호출하던 28개 파일의 30개 표현식에서
중복 호출만 제거했다. 포함·형제·드라이브 판정과 실제 경로 확인은 기존 Node API와 조건을
유지한다. 새 캐시를 추가하거나 파일시스템·소스·그래프·스타일·메모리 한도를 바꾸지 않는다.

원래 호출의 인수와 결과를 그대로 전달한 별도 계측은 다음 반복 작업을 확인했다.
계측 시간은 로딩 속도 근거로 사용하지 않는다.

| 대상        | 기존 resolve | 수정 resolve | 감소율 | native realpath | stat 조회 |
| ----------- | -----------: | -----------: | -----: | --------------: | --------: |
| VCM Section |      831,914 |      624,664 | 24.91% |   양쪽 15,171회 |  33,428회 |
| VCM IR      |      685,240 |      563,434 | 17.78% |   양쪽 25,471회 |  51,982회 |

상대 경로 판정 횟수는 각각 193,544회·123,381회로 같았고, CSS·의존성·진단·문맥·감시
디렉터리도 같았다. POSIX·Windows의 빈/상대 경로, 점 경로, 형제 접두사, 대소문자,
다른 드라이브·UNC 경계를 실제 Node 구현으로 확인하는 32개 회귀 검사를 추가했다.

계측을 끈 production 워커로 고정된 fast·corridor 화면 4개를 비교했다. 두 번의 AB/BA
반복에서 cold/warm 총 32회 모두 대상 출력과 ready에 도달했고, 16쌍의 CSS·의존성·진단·
페이지 구성·문맥·감시 디렉터리가 일치했다. 측정 중 다른 무거운 검사는 실행하지 않았다.

| 중앙값               |    기존 |    수정 | 감소율 |
| -------------------- | ------: | ------: | -----: |
| 첫 컴파일            | 14.30초 | 10.95초 | 23.43% |
| 반복 컴파일          | 11.49초 |  9.05초 | 21.26% |
| 첫 전체 로딩         | 19.77초 | 16.95초 | 14.28% |
| 반복 전체 로딩       | 16.76초 | 14.38초 | 14.17% |
| 첫 컴파일 Node CPU   | 18.64초 | 16.37초 | 12.15% |
| 반복 컴파일 Node CPU | 11.34초 | 10.20초 | 10.07% |

첫 전체 로딩은 8쌍 모두, 반복 전체 로딩은 8쌍 중 7쌍에서 빨랐다. 쌍별 시간 비율의
기하평균으로는 각각 16.30%·10.69% 감소했다. 개별 화면의 중앙값 회귀 10% 금지 기준도
통과했지만 IR 반복 전체 로딩은 3.81% 느렸다. 이 표본이 모든 파일과 실행 환경의 같은
개선율이나 모든 1분 이상 대기의 해소를 증명하지는 않는다. Node CPU에는 별도 native
esbuild와 브라우저 프로세스가 포함되지 않는다.

사용자는 속도를 위한 적당한 CPU 증가를 허용했다. 측정 전에 Node CPU 중앙값 50% 증가와
개별 쌍의 2배 증가를 제외 기준으로 정했고 제품 한도는 유지했다. 이번 후보의 CPU 비용은
감소했다. 앞선 구문 트리 공유 후보는 별도 32회 비교에서 IR 반복 로딩이 16.32% 느려져
원복했으며, 그 실패 결과를 이번 후보와 합치지 않았다.

실제 조합원 페이지의 1440×900·768×1024·390×844 스타일, Tab 포커스, 초대창 열기·취소와
두 번의 캐시 리로드를 비교했다. CSS와 계산된 스타일·동작이 같았고 스크린샷 12장을 직접
확인했다. 좁은 헤더의 기존 Inspector 주석 겹침과 실행 시점에 따른 trial 워터마크의 농도
차이는 남아 있다. 검증은 127.1.0.1과 CDP pipe로 수행했고 종료한 검증 브라우저의 임시
데이터는 각 실행 단위가 끝날 때 개별 보존 검사를 거쳐 정리했다.
