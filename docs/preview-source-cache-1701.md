# 소스 스냅샷 재사용 비용과 비동기 캐시 갱신 안정화

## 변경

`PreviewProjectFileAnalysisCache`에서 경로와 편집 내용이 정확히 같고 현재 byte 상한도
만족하면, 이미 검증한 UTF-8 길이와 UTF-16 지문을 재사용한다. 편집 내용이 다르거나 현재
상한이 더 작으면 기존 크기 검사와 지문 계산을 수행한다. 한글과 고립 서로게이트를 포함한
문자열 구분을 유지한다.

미완료 읽기는 경로별 소유권을 확인한다. 캐시 초기화·새 편집 내용·더 작은 byte 상한으로
이전 상태가 무효화되면, 이전 읽기의 성공이나 실패가 새 캐시 또는 새 미완료 읽기를
덮어쓰거나 제거하지 않는다. 파일 메타데이터나 Yarn 아카이브 검증을 기다리는 동안 등록된
새 스냅샷도 유지한다. 이전 요청 자체는 원래 읽은 결과나 실패를 그대로 받는다.

같은 byte 상한의 유효한 미완료 읽기는 계속 공유한다. 소유권은 미완료 읽기 동안만 보관하고
완료·편집 교체·초기화 시 제거한다. 소스 128MiB·16,384개 및 기존 분석 캐시 상한은 그대로다.
새로운 상주 서비스나 예약 작업은 만들지 않는다.

## 성능 측정의 범위

실제 VCM 편집 내용 7,653byte와 검색 페이지 4,853byte로 같은 스냅샷을 각각 2,000번
재사용했다. 수정 전·후 순서를 교대한 7회 중앙값은 다음과 같다.

| 재사용 구간 | 수정 전 | 수정 후 |
| ----------- | ------: | ------: |
| VCM         | 23.68ms |  2.28ms |
| 검색 페이지 | 15.18ms |  1.42ms |

이 수치는 스냅샷 캐시 구간의 비용이며 전체 프리뷰 준비 시간이나 모든 프로젝트의 속도
개선율을 뜻하지 않는다. 실제 빌드 비교와 별도로 해석한다. 결과 record의 내용과 지문은 같다.

## 검증

- 기존 코드에서 실패하는 초기화·동시 읽기·새 스냅샷의 경쟁 조건을 먼저 재현했다.
- 더 작은 byte 상한으로 새 스냅샷이 제거된 경우에도 이전 읽기를 되살리지 않는다.
- 느린 메타데이터 조회의 성공·변경·실패·용량 초과가 새 편집 상태를 덮어쓰지 않는다.
- 기존 디스크·Yarn zip·렌더 사실·import 사실 재사용과 상위 문맥 캐시 검사를 유지한다.
- 전체 `npm run check`: 738개 파일·5,795개 테스트, 줄 수·타입·린트·포맷·빌드 통과.
- 설치된 0.1.1700과 수정본을 VCM·검색 페이지에서 순서를 교대해 16번 준비했다. 문맥,
  의존성 목록·메타데이터, 모든 CSS와 청크 수는 같고 새 오류·경고 종류는 없다.
  기존 경고의 첫 참조 위치와 재준비 때의 표시 횟수는 실행별로 다르다.
- VCM의 JavaScript 청크 이름·지문은 수정 전 코드 자체의 첫 준비와 재준비에서도 달라진다.
  전체 JavaScript의 바이트 일치를 검증했다고 주장하지 않는다.
- 추가 계측에서 검색 페이지의 소스 요청은 모두 3,022회였고 재준비의 디스크 읽기는
  수정 전·후 모두 15회였다. 최초 읽기는 833→834회다. 제품 코드에는 계측을 넣지 않았다.
- 실제 전체 준비 시간은 표본별 편차가 크고 검색 페이지가 수정 후 더 느린 실행도 있었다.
  이 표본으로 전체 준비 속도 향상을 확인했다고 주장하지 않는다. CPU·RSS·원시 시간과
  불리한 표본도 함께 보존한다. 네이티브 창의 시각 검증은 이번 변경에서 수행하지 않았다.
